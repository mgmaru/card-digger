# `created`と`updated`の追加観測結果

## 判定

| 質問 | 結果 |
|---|---|
| **1. 編集で`created`は動くか** | **動かない。** 347件中254件が「更新されたが`created`はそのまま」 |
| **2. 商品ページはどちらを表示しているか** | **`updated`。** 3 / 3で一致 |

この2つから、`created`について言えることが確定した。

| 主張 | 状態 |
|---|---|
| 編集・再出品で`created`は動かない | **確定**（n=347） |
| 商品ページは`created`を表示しない | **確定**（3 / 3で`updated`） |
| `created`は**出品日時**である | **検証手段が無い**（`unverifiable`） |

`created`は**動かない安定した「始まりの時刻」**であることまでは実測で言える。
それを「出品日時」と呼ぶ最後の一歩だけが、照合相手が無いため確認できない。

`updated`は**商品ページが商品の経過時間として表示している値**であり、`observed`とする。
ページ側にラベル文字は無いため、「Mercariが更新日と呼んでいる」ことまでは確認していない。

## 2. 質問1 — 編集で`created`は動かない

| 指標 | 実測 |
|---|---:|
| 検索で得た商品 | **347件** |
| `created == updated`（一度も更新されていない） | 93件 |
| **`updated > created`（更新されたが`created`は動いていない）** | **254件** |
| `updated < created`（説明できない） | **0件** |
| 差の中央値 | 1.7日 |
| 差の最大 | **182.0日** |

**254件が「更新されたのに`created`はそのまま」である。** 182日後に更新された商品でも
`created`は動いていない。矛盾する順序（`updated < created`）は0件だった。

「編集や再出品で`created`がリセットされるのではないか」という懸念は**否定された。**

### 縦断観測は不要だった

当初この問いは「1〜2日待って同じ商品を再取得する」ものと考えていた。
**同時刻に`created`と`updated`を並べれば足りる。** 両者が離れている商品が存在すること自体が、
「`created`は最終更新時刻ではない」ことの証拠になる。

## 3. 質問2 — 商品ページは`updated`を表示している

| 標本 | ページ表示 | `created`換算 | `updated`換算 | 一致 |
|---:|---|---|---|---|
| 1 | 1時間前 | **10日前** | 1時間前 | **`updated`** |
| 2 | 1時間前 | 4時間前 | 1時間前 | **`updated`** |
| 3 | 1時間前 | **2日前** | 1時間前 | **`updated`** |

`created`が10日前・2日前と大きく離れた標本でも、ページは`updated`を表示した。

### ページ側の表示

商品ページの経過時間は`item-detail-container`（商品自身の情報欄）の中に**1つだけ**あり、
**ラベル文字が無い**（「更新」とも「出品」とも書かれていない）。

日付らしい表示（`YYYY年MM月DD日` / `N日前` / `N時間前` / `出品日` / `掲載日`）を
全要素から検索したが、該当はこの1件のみだった。**`created`に相当する表示は存在しない。**

## 4. 1回目の実行は失敗した

最初の実行では3件とも判定できなかった。**原因はMercari側ではなく、標本選択の設計ミス。**

| # | 誤り | 影響 |
|---|---|---|
| 1 | `updated`が0〜1分前の商品ばかり選んでいた | 分単位のラベルは不安定で判定に使えない |
| 2 | 現在時刻を実行開始時に1度しか計算していなかった | ページ取得は数分後。分単位の判定が時間差で壊れる |

「ラベルが違うこと」だけを選定条件にしていたため、**極端に新しい商品が選ばれた。**

修正して、両方の時刻が1時間以上前であることを条件に加え、現在時刻をページ取得のたびに
読み直すようにした。Testで固定している。

```python
def test_a_listing_updated_moments_ago_is_rejected(self):
    """The first run picked three such listings and learned nothing from any of them."""
```

失敗した実行のRequest（API 3件 / ページ3枚）も通算に含めて記録する。

### `unverifiable`という区分

`assumed`（まだ検証していない）と区別する。

| 区分 | 意味 | 扱い |
|---|---|---|
| `assumed` | **まだ検証していない** | 塞ぐべきTask。放置しない |
| `unverifiable` | **検証する手段が存在しない** | **塞げない。** 限界として明示する |

`created_at`は後者である。商品ページに照合相手が無く、待っても現れない。

## 7. Productとして考えるべきこと

`created`と`updated`は「古さ」の意味が異なる。

```text
created が古い    長く存在している出品
updated が古い    出品者が長く触っていない出品
```

「引退品で放置されているもの」を探すという目的からすると、**どちらが適切かは自明ではない。**
現在のMVPは`created`だけを扱い、`updated`はDomain型に持っていない。

これは正しさの問題ではなく**Productの決定**であり、Phase 1のUI設計時に判断する。
`updated`は3経路すべてで取得でき、Fork変更なしでDomain型へ追加できる。
