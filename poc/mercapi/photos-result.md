# 商品画像の枚数と、複数枚表示の速度

## 判定

| 質問 | 結果 |
|---|---|
| **1. 検索は1出品あたり何枚のURLを返すか** | **1枚だけ。** `photos`も`thumbnails`も120 / 120で1枚。0枚も2枚以上も無い |
| **1b. 商品詳細は何枚返すか** | **中央値2枚、最大9枚。** ただし**20件中6件は詳細でも1枚**のまま |
| **2. その画像は状態を判断できる大きさか** | **できる。** 幅1080px（最小810）、JPEG、1枚あたり中央値177KB。20 / 20がデコード成功 |
| **3. 一覧で複数枚出すと画面は遅くなるか** | **描画は問題ない**（4枚で1.2倍、+109ms）。**成立しないのは描画ではなくURLの取得側** |
| **4. 今のやり方（Mercariを開く）はいくらか** | **1,796ms**（`load`まで。写真を探して開く時間を含まない**下限**） |

**この観測の前に立てていた見立ては外れていた。**「Adapterは`photos`を全部転記していて、
残りの写真はブラウザまで届いているのに捨てられている」と書いたが、**届いていたのは1枚だけ**だった。
Adapterの転記は正しく、**転記する元が1枚しかない。**

**結論の形が変わる。** 一覧の全Cardで複数枚見せるには**1出品につき詳細1 Request**が要り、
120件では[2秒間隔](../../docs/development/architecture.md#41-外部アクセスの条件と2秒間隔の出所)で
**240秒**になる。検索1回20〜30秒（[MVP仕様 §5.3](../../docs/product/mvp-spec.md#53-収集範囲)）の
道具に載らない。**利用者が選んだ1件だけなら、詳細1回243msで載る。**

## 1. 検証目的

**「まとめ売りの状態を確かめるためにMercariを開いて戻る」往復を、アプリ内で終わらせられるか。**

利用者の見送り理由は現時点で1つで、**「開いて、写真を見て、状態が悪いのでやめる」**である。
一覧のCardに状態（[MVP仕様 §5.6](../../docs/product/mvp-spec.md#商品の状態2026-09-04決定)）は
出ているが、**出品者が束1つに付けた申告値1個**なので、写真で確かめてから決めている。

時間が溶けているのは**判断**ではなく**往復**である。判断は2秒で終わる。

したがって問いは2段になる。

1. **アプリが写真を持っているか。**持っていれば表示するだけ。持っていなければ、いくらで買えるか
2. **表示して遅くならないか。**遅くなるなら、往復を消しても差し引きで損をする

**[Phase 2「まず測る2件」の2件目](../../docs/planning/todo.md#まず測る2件)がこの1つ目にあたる。**
当初はRequest設計を決めるための測定だったが、利用者の不便に直接答える測定へ変わった。

**手段（画像解析）から目的を決めない**という同節の方針に従い、
**画像解析を使わずに往復が消えるか**を先に測る。

| Keyword | **`ポケカ 引退品`**（[`poc/common/conditions.json`](../common/conditions.json)の固定検索語） |
| 認証状態 | 匿名。Login / 永続Cookie / 明示Token / Proxyなし |

**判定規則は実行前にコードへ書いてある。** 測ってから基準を選ばないためで、
規則そのものは[`test_photos_probe.py`](test_photos_probe.py)が固定している。

| 規則 | 中身 |
|---|---|
| 枚数の数え方 | 空白URLは枚数に数えない。**平均を出さず分布を残す**（1枚が半分・8枚が半分と、全部4枚は別の画面になる） |
| 「見られる」の判定 | HTTP 200は写真であることを意味しない。**デコードして画素サイズを見る。** 短辺がCardの枠（200px）未満なら引き伸ばしになる |
| 描画の測り方 | **1画面（fold）の中に枠が始まる`<img>`が全部デコードし終わるまで。** ページ自身の時計で測る |
| 繰り返し | **各条件5回、中央値で比較。**最小・最大も併記する |

**Card枠・Grid・画像枠は`ItemGrid.module.css`と`ItemCard.module.css`と`tokens.css`から
写している**（`--grid-min: 200px`、行32px / 列24pxのgap、画像は`aspect-ratio: 1`の`object-fit: cover`）。
1画面に入る画像の枚数が実物と違えば、この測定には意味が無い。

### 追加した規則が1つある（実行後）

**1回目の実行で、`4枚`条件の1回が「画像Request 1件・デコード0件・18,140ms」になった。**
これを「4枚は遅い」と数えると**結論が正反対になる。**何も読み込めておらず、何も計測していない。

> **1画面の画像が1枚でもデコードされなかった回は、測定として数えない。**

割合の閾値にしなかったのは、出所が無いためである。厳密にしておけば、
標本に本当に壊れた画像があるときは**有効0回**として見えるので、中央値が静かにずれない。
**この規則は実行後に足した。**本番の実行では除外0回だった。

## 3. 条件

| 条件 | 値 |
|---|---|
| 同時実行数 | 1 |
| Request開始間隔 | 2秒以上 |
| 自動再試行 | **0回** |
| 拒否・安全停止 | **なし**（HTTPは全件200） |
| 検索 | **1ページ**（アプリの収集は複数ページだが、枚数の問いに2ページ目は要らない） |
| 商品詳細 | 20件 |
| 画像本体 | 20枚 |
| 描画 | 20 Card × 3条件 × **5回**。**条件ごとに新しいBrowser**（cold cache） |
| 商品ページ | 3件 × 5回 |

**描画の3条件は、同じ20出品・同じviewport・同じCSSで、1 Cardあたりの枚数だけを変える。**

| 条件 | 中身 |
|---|---|
| **1枚（現状）** | 今のCard。先頭1枚だけ |
| **4枚** | 先頭1枚 + その下に横並び3枚 |
| **全枚数** | 先頭1枚 + 詳細が返した残り全部 |

`loading="lazy"`は3条件とも付けたままにした。**実物のCardがそうだから**である。

### Requestの実数

| 種類 | 件数 |
|---|---:|
| Mercari API（検索1 + 詳細20） | **21** |
| 画像（本体20 + 描画測定650） | **670** |
| 商品ページ読み込み | **15** |

**画像670件はCDNの静的Assetで、APIではない。** ブラウザが今も同じ経路で取っており、
Mercariの検索結果を1画面スクロールするのと同じ桁である。

## 4. 結果

### 4.1 検索は1枚しか返さない

| 指標 | `photos` | `thumbnails` |
|---|---:|---:|
| 出品 | 120件 | 120件 |
| **0枚** | **0件** | **0件** |
| **1枚** | **120件** | **120件** |
| **2枚以上** | **0件** | **0件** |
| 最小 / 中央値 / 最大 | 1 / 1 / 1 | 1 / 1 / 1 |

Adapterが選んだのは`photos`（120 / 120）。**欠落は0件**で、
[Adapter仕様](../../docs/phase-0/phase-0-f-adapter-spec.md)の`observed`は正しい。
**枚数が1だっただけである。**

### 4.2 商品詳細は複数枚返すが、3割は1枚のまま

| 指標 | 実測 |
|---|---:|
| 標本 | 20件 |
| **1枚** | **6件（30%）** |
| **2枚以上** | **14件（70%）** |
| 最小 / **中央値** / 最大 | 1 / **2** / 9 |
| 詳細1回の所要（中央値） | **242.6 ms** |
| 同（最小〜最大） | 120.8〜351.5 ms |

枚数の内訳。

| 枚数 | 1 | 2 | 3 | 4 | 5 | 7 | 8 | 9 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 出品 | **6** | 6 | 2 | 1 | 2 | 1 | 1 | 1 |

**3割は、Mercariを開いても写真が増えない。** 出品者が1枚しか載せていないためで、
これは取得方法では改善しない。**逆に言うと、その3割については「開く価値が無い」と
アプリが言える。**

### 4.3 画像は状態を判断できる大きさだった

| 指標 | 実測 |
|---|---:|
| 標本 | 20枚 |
| HTTP 200 | **20枚** |
| **デコード成功** | **20枚** |
| 短辺200px以上 | **20枚** |
| 幅 最小 / 中央値 / 最大 | **810 / 1080 / 1080 px** |
| 1枚あたりbytes（中央値） | 177,155 |
| 形式 | JPEG 20枚 |

URLは`static.mercdn.net`で、**リサイズ指定（`w=`）を持たない**（62 / 62）。
`c!/w=240`のような縮小版ではなく、**そのまま出せる大きさ**である。

**「枚数はあるが小さすぎて状態が見えない」という落とし穴は無かった。**

### 4.4 描画は、枚数を増やしても壊れない

**中央値で比較。除外0回。**

| 条件 | 1画面の画像 | **出そろうまで** | 最小〜最大 | idleまで | Request | bytes |
|---|---:|---:|---:|---:|---:|---:|
| **1枚（現状）** | 15枚 | **551 ms** | 470〜1,151 ms | 1,129 ms | 20 | 3.97 MB |
| **4枚** | 28枚 | **660 ms** | 609〜1,329 ms | 1,434 ms | 48 | 9.20 MB |
| **全枚数** | 41枚 | **1,325 ms** | 952〜2,227 ms | 2,298 ms | 62 | 11.97 MB |

| 条件 | 現状比 | 差 |
|---|---:|---:|
| 4枚 | **1.2倍** | **+109 ms** |
| 全枚数 | **2.41倍** | **+774 ms** |

**Request数とbytesは枚数に比例して増えるが、時間はそこまで増えない。** ブラウザが並行に取り、
`loading="lazy"`が画面外を後回しにするためである。

**ただし最小〜最大が重なっている。** `1枚`の最大1,151msは`4枚`の中央値660msより大きい。
**`4枚`の+109msは、この測定のばらつきの中にある。** `全枚数`の+774msは中央値どうしで
区別が付くが、それでも最小952msは`1枚`の最大1,151msより速い。

### 4.5 今のやり方は1.8秒（下限）

| 指標 | 実測 |
|---|---:|
| 開いたページ | 15回 |
| **`load`まで（中央値）** | **1,796 ms** |
| 最小〜最大 | 1,692〜12,126 ms |

15回中14回は1,692〜2,132msに収まり、1回だけ12,126msだった。

**これは下限である。** `load`はブラウザが待つのをやめた時刻で、
**読み手はそこから写真を探し、開き、めくり、戻る。** 実際の往復はこれより長い。

## 5. 決まったこと

### 5.1 一覧で全Cardに複数枚出すのは、成立しない

**描画が理由ではない。** 4枚は+109msで、これは「著しく遅い」に当たらない。

**URLを手に入れる側が成立しない。**

| | Request | 2秒間隔での所要 |
|---|---:|---|
| 検索結果120件ぶんの詳細 | **120** | **240秒（4分）** |
| 検索1回（[§5.3](../../docs/product/mvp-spec.md#53-収集範囲)） | — | 20〜30秒 |

**検索の10倍かかる。**[Phase 2の「一括解析は成立しない」](../../docs/planning/todo.md#一括解析は成立しない1商品ずつになる)と
同じ結論に、画像解析を持ち出す前に到達している。

### 5.2 利用者が選んだ1件なら、成立する

| | 所要 |
|---|---:|
| **アプリ内: 詳細1回 + 写真表示** | **243 ms**（画像は中央値2枚 × 177KB） |
| **今: Mercariの商品ページを開く** | **1,796 ms（下限。探して開いて戻る時間を含まない）** |

**アプリ内のほうが速い。** そして往復そのものが消える。

**2秒間隔は1回の所要ではない。**「前のRequestからの間隔」なので、
利用者が1件ずつ開く限り、体感は実測の243msになる。連続で開けば2秒待つ。

### 5.3 画像解析は、この不便には要らない

**[Phase 2の地雷の分類表](../../docs/planning/todo.md#まず測る2件)で言えば、
「写真を見ないと分からない」で正しい。** ただし**必要なのは写真を「見せる」ことであって、
「解析する」ことではなかった。**

| | 問い | 要るもの |
|---|---|---|
| 利用者が写真でやっていること | この束、傷んでいないか | **写真を出すだけ** |
| [Phase 2の実装一覧](../../docs/planning/todo.md#実装--測定と決定の後) | この束に何が入っているか | OCR・カード同定 |

**依存も増えない。** Local model（OpenCV / ONNX / Tesseract）も外部Vision APIも要らないので、
[Phase 2の決める4件](../../docs/planning/todo.md#測ってから決める4件)のうち
**4番（解析をどこで走らせるか。`.env`を導入するか）は、この用途では起きない。**

### 5.4 まだ決めていないこと

- **3割の「1枚しかない」出品をどう見せるか。** 詳細を取って初めて分かる。
  「1枚だけ」と分かること自体に価値があるが、**それを知るのに1 Request要る**
- **写真を出す形**（Card内で展開・別画面・Overlay）。[視覚方針](../../docs/product/design-tokens.md)が持つ判断
- **説明文を一緒に取るか。** 詳細Responseは`description`も持っている。
  同じ1 Requestで手に入るので、**取らない理由のほうが要る**

### 5.5 この観測で外していた見立て

| 観測前に書いたこと | 実測 |
|---|---|
| 「残りの写真は既にブラウザまで届いていて、捨てられている」 | **届いていない。**検索は1枚しか返さない |
| 「Frontendだけの変更で、追加Requestは0」 | **1件につき1 Request要る** |

**Adapterの実装は正しかった。**`photos`を全部転記しており、
**転記する元が1枚だっただけである。**「全部転記している」を「全部届いている」と読んだのが
誤りで、**枚数を数えずに結論を書いた**ことがそのまま原因である。
