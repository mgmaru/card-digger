# Phase 0 共通検証プロトコル

## 1. 目的

`marvinody/mercari`、`kynacio/mercapi`、Playwrightの3方式を、同じ入力・停止条件・評価方法で比較する。検証結果の差が検索条件や測定方法の違いではなく、取得方式の違いから生じる状態を作る。

一部の項目を取得できなくても、アクセス上の安全停止条件に該当しない限り、残りの項目の検証は継続する。取得不能・非対応・解析失敗も結果として残し、次の方式を試すための判断材料にする。

実行時の正本は[`poc/common/conditions.json`](../../poc/common/conditions.json)とする。この文書は値の意味と測定手順を定義する。

## 2. 固定する検索条件

| 項目 | 値 | 理由 |
|---|---|---|
| キーワード | `ポケカ 引退品` | MVPの中心ユースケースであり、一定数の検索結果が期待できる |
| 販売状態 | `on_sale`（販売中） | 購入候補だけを対象にする |
| 並び順 | `created_time ASC`（古い順） | 本アプリが解決したい主要課題を直接検証する |
| カテゴリ | 指定なし | 方式ごとのカテゴリ体系や絞り込み差を持ち込まない |
| 最低・最高価格 | 指定なし | 取得可能範囲を価格で狭めない |
| 認証状態 | ログインなし | 個人アカウントや永続Cookieへの依存を避ける |
| ロケール・タイムゾーン | `ja-JP` / `Asia/Tokyo` | 日時表示と記録条件を統一する |

古い順指定を受け付けない方式でも検証は継続し、実際に使用された並び順、クライアント側ソートの有無、最古商品の日時を記録する。取得後のクライアント側ソートだけでは「古い商品まで遡れる」と判定しない。

## 3. 共通の取得モデル

各方式のレスポンスを次の項目へ正規化する。元レスポンスのフィールド名と、追加リクエストまたは値の生成が必要だったかも記録する。

| 項目 | 正規化ルール |
|---|---|
| `itemId` | 空でない文字列。ページ間の重複判定キーに使う |
| `title` | 空でない商品タイトル |
| `priceYen` | 1円以上の整数。通貨は日本円 |
| `itemUrl` | `https` の商品URL。IDから生成した場合は `generated` と記録する |
| `imageUrls` | `https` のURL配列。最低1件を取得成功とする |
| `createdAt` | 解析後はRFC 3339形式で保存し、元の値も検証ログに残す |
| `listingStatus` | 販売状態。`on_sale` / `sold_out` / `unknown` のいずれか |
| `itemCondition` | 商品コンディション。取得元のID・表示名・生値を保持し、取得不能時は `null` |
| `likeCount` | いいね数。0以上の整数。取得不能時は `null`。`isLiked`のような真偽値で代用しない |
| `sellerId` | 空でない文字列。取得不能時は `null` |
| `sellerName` | 空でない文字列。取得不能時は `null` |

検索結果の商品フィールドは最初の100ユニーク商品を母数にする。商品詳細が必要な `itemCondition` と `likeCount`、画像本体取得は、取得順で最初の20商品を共通標本とする。Seller情報とSellerの商品一覧は、取得順で最初に現れる10人のユニークなSellerを母数にする。

## 4. 実行環境の記録

検証結果には次を必ず記録する。

- 実行日時とタイムゾーン
- GitコミットSHA
- OS、CPUアーキテクチャ
- PythonまたはNode.jsのバージョン
- 対象ライブラリのバージョンまたはコミットSHA
- 直接依存パッケージとバージョン
- Headless / Headedの別
- Cookie、Token、ログイン、Proxyの要否（値そのものは記録しない）
- 実行したコマンド

市場の検索結果は時間とともに変化するため、3方式の本測定は可能な限り同じ端末・ネットワークで24時間以内に行う。

## 5. 測定手順

以下の外部リクエストはすべて同時実行数1、リクエスト間隔2秒以上で行う。**この値がここで初めて置かれた。**
出所と、なぜ保守的でよいかは[アーキテクチャ §4.1](../development/architecture.md#41-外部アクセスの条件と2秒間隔の出所)を正本とする。
方式固有の制約で条件を守れない場合は、差異と理由を結果へ記録する。

### 5.1 検索安定性

1. 各試行を新しいプロセスで実行し、前回のインメモリ状態を引き継がない。
2. 同じ検索条件で5回試行する。
3. 自動再試行は行わない。再試行を実装した測定は補足結果として分離する。
4. 試行間およびページ間は2秒以上空け、同時実行数は1とする。
5. 各試行の成否、エラー分類、処理時間、取得件数を記録する。

1回の検索成功は、60秒以内に処理が完了し、致命的な通信・解析エラーがなく、必須項目を持つ商品を1件以上返した場合とする。

### 5.2 ページングと古い商品

ページングは1回の独立した測定として、次のいずれかまで継続する。

- 100ユニーク商品以上を取得し、365日以上前の商品を1件以上取得した
- 次ページが存在しない
- 20ページに到達した
- 1,000ユニーク商品に到達した
- 安全停止条件に該当した

ページ番号またはCursor、ページごとの件数、重複商品数、累計ユニーク件数を記録する。「十分古い商品」の暫定基準は検証実行日時から365日以上とする。

### 5.3 Seller情報

商品から取得できたSeller IDを出現順に重複排除し、最大10人についてProfileを取得する。Seller ID、Seller名、Profile取得成否、追加リクエスト数、エラーを記録する。

各Sellerについて、`on_sale` と `sold_out` を分けて商品一覧を取得する。状態フィルターを指定できない方式では一覧を取得後に `listingStatus` で分類し、その事実を記録する。各Seller・各販売状態について、次のいずれかまでページングする。

- 20ユニーク商品を取得した
- 次ページが存在しない
- 5ページに到達した
- 100ユニーク商品に到達した
- 安全停止条件に該当した

レスポンスが正常に解析できれば、商品が0件でもEndpoint呼び出し自体は成功とする。商品一覧取得成否、販売状態別の件数、ページング、重複数、取得フィールド、追加リクエスト数を記録する。売却済み一覧を提供しない方式は `unsupported` として失敗を隠さず記録する。

### 5.4 商品詳細、いいね数、商品コンディション

取得順で最初の20商品について商品詳細を取得し、次を確認する。

- `likeCount` を0以上の整数として取得できるか
- `itemCondition` のIDまたは表示名を取得できるか
- 検索結果だけで取得できるか、商品詳細への追加リクエストが必要か
- 生レスポンスのフィールド名と、正規化に必要な変換

`isLiked`、`liked`など「現在の利用者がいいねしたか」を表す真偽値は、いいね数として数えない。値が0の場合は取得成功とする。

### 5.5 画像本体のWeb取得

取得順で最初の20商品の先頭画像URLについて、アプリケーションが動く環境から実際にHTTP GETする。HEADリクエストだけでは成功と判定しない。

次をすべて満たした場合に画像本体の取得成功とする。

- 30秒以内に完了した
- Redirectが5回以内で、最終HTTP Statusが200〜299だった
- `Content-Type` が `image/` で始まる
- Bodyが1byte以上、20MiB以下だった
- JPEG、PNG、WebP、GIF、AVIFのいずれかとしてデコードできた

最初はログインCookie、認証Token、Refererなしの匿名GETを行う。失敗した場合は、同じPoC実行中の公開セッション情報を利用した取得を補足試験として実施できるが、匿名取得と結果を分け、必要になったHeaderやCookieの種類だけを記録する。画像Bodyは検証後に破棄し、Gitへ保存しない。

## 6. 指標と合格目安

| 指標 | 算出方法 | 合格目安 |
|---|---|---:|
| 検索成功率 | 成功試行数 / 5 | 80%以上。100%を優先 |
| 取得件数 | ユニークな`itemId`数 | 100件以上 |
| 重複率 | 重複出現数 / 全出現数 | 参考値として比較 |
| 必須項目取得率 | ID・タイトル・価格・URL・販売状態を取得できた商品数 / 対象商品数 | 各100% |
| 画像URL取得率 | 画像URLを1件以上取得できた商品数 / 対象商品数 | 95%以上 |
| 画像本体取得率 | HTTP GETと画像デコードに成功した商品数 / 画像標本数 | 95%以上 |
| 出品日時取得率 | 正常に日時解析できた商品数 / 対象商品数 | 95%以上 |
| 商品コンディション取得率 | IDまたは表示名を取得できた商品数 / 詳細標本数 | 95%以上 |
| いいね数取得率 | 0以上の整数を取得できた商品数 / 詳細標本数 | 95%以上 |
| Seller ID取得率 | Seller IDを取得できた商品数 / 対象商品数 | 95%以上 |
| Seller名取得率 | Seller名を取得できたSeller数 / Seller標本数 | 90%以上 |
| Seller商品一覧取得率 | 正常な一覧レスポンスを取得できたSeller数 / Seller標本数 | 販売状態ごとに90%以上 |
| Seller商品ページング | 2ページ目へ進めたか、1ページで終端したことを判定できたか | Seller・販売状態ごとに記録 |
| 古い商品到達 | 出品から365日以上の商品を取得したか | 1件以上 |
| 実行速度 | プロセス全体と検索処理の経過時間 | 中央値・最大値を比較 |
| HTTP/APIエラー | 401 / 403 / 429 / Timeout / Parse Errorの件数 | 0件を優先 |

閾値未達でも測定値は破棄しない。必須情報を追加の商品詳細リクエストで補える場合は、補完後の取得率、総リクエスト数、追加時間を分けて記録する。

## 7. 実装・保守性の比較

### 実装の複雑さ

次の客観値を記録してから、`低 / 中 / 高` を判定する。

- PoCの実コード行数（生成物とテストデータを除く）
- 直接依存パッケージ数
- 初回セットアップのコマンド数
- Browser、Cookie、Token、手作業の要否
- ページング、レスポンス変換、再試行に必要な独自コード

### Mercari仕様変更への耐性

次を根拠に `低 / 中 / 高` を判定する。

- 非公開Endpoint、レスポンス構造、DOM、通信Interceptへの依存範囲
- 外部ライブラリ内に変更影響を閉じ込められるか
- 型定義・自動テスト・固定レスポンスFixtureの有無
- 対象プロジェクトの更新状況
- 破損を検知できるエラー処理とテストの有無

## 8. エラー分類と安全停止

エラーは少なくとも `unauthorized_401`、`forbidden_403`、`rate_limited_429`、`timeout`、`parse_error`、`challenge`、`network_error`、`image_content_type_error`、`image_too_large`、`image_decode_error`、`unsupported`、`unknown` に分類する。

次の場合はアクセスを停止し、回避を試みず結果へ記録する。

- 401、403、429、Challenge/CAPTCHAが合計3回連続した
- 対象サービスが待機時間を明示した
- 予期しない大量リクエストが発生する挙動を確認した

Rate Limitは通常のPoC実行中に受動的に観測する。制限値を特定するための高負荷試験は行わない。認証回避、CAPTCHA回避、複数アカウント・Proxyによる制限回避も検証対象外とする。

## 9. 結果の保存

各PoCの結果は[`poc/common/result-template.md`](../../poc/common/result-template.md)をコピーし、方式ごとのディレクトリへ`result.md`として保存する。

生レスポンス、画像Body、スクリーンショット、Traceは各方式の `artifacts/` に一時保存できるが、Git管理外とする。結果MarkdownへCookie、Token、個人情報を転記せず、必要な例示データはマスクする。
