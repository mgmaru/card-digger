# ADR 0004 — 出品者リストをローカルのファイルへ保存する

| 項目 | 内容 |
|---|---|
| 状態 | **決定（2026-11-19）。**論点1・3は利用者が決めた。**論点2（ファイルの形式と置き場所）は実装者が選んだ値で、利用者の確認を待つ**。**2026-11-20に論点1へ「読み手自身の評価」を足した**（[論点1の追記](#2026-11-20の追記--読み手自身の評価を保存する)） |
| 決める人 | 利用者 |
| 覆すもの | [MVP仕様 §4](../product/mvp-spec.md#4-mvpに含めない機能)の「お気に入り、確認済みFlag、商品・Seller Memo」と、[§10](../product/mvp-spec.md#10-data取扱い)の「商品・Seller情報をDatabaseへ保存しない」の**適用範囲** |
| 使う仕様 | [出品者探索 実装仕様](../product/seller-discovery-spec.md) |

## 背景

Card Diggerは**何も保存しない**道具として作った。[MVP仕様 §10](../product/mvp-spec.md#10-data取扱い)が
「商品・Seller情報をDatabaseへ保存しない」と定め、[§4](../product/mvp-spec.md#4-mvpに含めない機能)が
お気に入りやSeller Memoを対象外にしている。**どちらも「MVP完成後に、価値と運用条件を再評価して追加する」**
という前提で外したものである。

2026-11-19に利用者がMercariを4時間ほど巡回し、次のことを述べた。

| 利用者が述べたこと | 意味 |
|---|---|
| 価値を分からずに出している出品者は、**ポケカだけでなく服や生活用品も出品している**傾向がある | 探す単位を「商品」から「出品者」へ変えられる |
| **出品者を探すのがかなり大変**である。ここを自動化したい | 1人ずつ手で開く作業を、道具が引き受ける価値がある |
| **検索する出品者を保存しておく**のが良い | 見つけた出品者を覚えておく場所が要る |
| **良くない出品者は検索から除外する**のが良い | 見ないと決めた出品者を覚えておく場所が要る |

**下の2行は、何かを保存しないと満たせない。**画面を閉じれば忘れる道具には載らない。
再評価する条件が揃ったので、ここで方針を変える。

## 論点1 — 何を保存するか

### 選択肢

| | A. 読み手の決定だけ | B. 決定 + 出品者の名前 | C. 決定 + 調べた結果ぜんぶ |
|---|---|---|---|
| 保存するもの | Seller ID、どちらのリストか、追加した日、読み手のメモ | Aに加えて、追加した時点の名前 | Bに加えて、評価の内訳・出品の幅・調べた日時 |
| 一覧の読みやすさ | **低い。**IDとメモしか出ない | 高い | 高い |
| 古くなるもの | **無い。**どれもMercariの事実ではない | 名前（出品者が変えられる） | 名前・評価・出品の幅のすべて |
| [§10](../product/mvp-spec.md#10-data取扱い)との距離 | **近い。**「商品・Seller情報」を1つも持たない | Seller情報を1つ持つ | Seller情報を持つ。**Cacheそのもの**であり、[O-5](../planning/todo.md#オプション--判断済みで保留しているもの)が保留している理由（鮮度の根拠が無い）がそのまま当たる |

### 決定 — A

**保存するのは、読み手が下した決定だけである。**出品者についてMercariが言ったことは、1つも保存しない。

| 保存する | 保存しない |
|---|---|
| Seller ID | 出品者の名前 |
| リストの種別（保存 / 除外） | 評価・評価件数 |
| 追加した日時 | 出品・商品・画像 |
| 読み手のメモ（200字まで） | 出品の幅、Seller Knowledge、調べた結果 |

理由は2つある。

1. **§10の趣旨が残る。**§10が避けたかったのは「他人の情報を手元へ溜めること」であり、
   Aのファイルにあるのは「私はこの出品者についてこう決めた」という読み手自身の記録である。
   IDは決定の宛先として要る最小のものである
2. **古くならない。**保存したものが事実とずれる、という問題がそもそも起きない。
   名前も評価も、出品者を開いたときにMercariから取得する

### 分かっている代償

**出品者リストの画面に名前が出ない。**出るのはSeller IDとメモである
（[出品者探索 §6](../product/seller-discovery-spec.md#6-出品者リスト)）。
メモを書かなければ、数字の並んだ一覧になる。

**これは使ってみて見直す前提の値である。**不便が大きければBへ進む。Bへ進むときは、
この論点を書き直し、保存するFieldを足す。**Cへは進まない。**CはCacheであり、
[O-5](../planning/todo.md#オプション--判断済みで保留しているもの)を先に解く必要がある。

### 2026-11-20の追記 — 読み手自身の評価を保存する

**使ってみた結果、Bへは進まなかった。**利用者が一覧を見て、こう決めた。

| 利用者が述べたこと | 決まったこと |
|---|---|
| 名前は保存する必要がない。出品者が名前を変えたら分からなくなる | **Bへ進まない。**名前は保存しないままにする |
| メモで区別を付けるほうが良い | 区別するのは、読み手が書いたものである |
| メモだけで使いづらければ、出品者ごとに自分で評価を付けて、優先して確認する相手を見分けたい | **読み手自身の評価を、保存するものに足す** |
| 総合的な評価だけだと、どんなカードを出す出品者なのかが抽象化されて分からなくなる。細かく評価したほうが、早く決められる | **総合評価は置かない。軸ごとに付ける** |

**これはAの範囲の中である。**Aが保存を許しているのは「読み手が下した決定」で、
禁じているのは「出品者についてMercariが言ったこと」である。読み手が付けた評価は前者であり、メモと同じ側にある。

| 保存する（足したもの） | 中身 |
|---|---|
| 状態の評価 | 3段階、または未評価。美品が多いか |
| 出品頻度の評価 | 3段階、または未評価。よく出品するか |
| 価格の評価 | 3段階、または未評価。相場より安く出すか |
| 評価した日時 | 評価を最後に変えた日時 |

**保存しないものは、1つも変わらない。**名前、Mercariの評価・評価件数、出品、出品の幅、調べた結果は、今も保存しない。

**Mercariの「評価」と、ここで言う「評価」は別のものである。**前者は取引の相手が付けたもので、Mercariが言ったことである。
後者は読み手が自分で付けたもので、保存する。画面と文書では、後者を「自分の評価」と書いて区別する。

#### なぜ軸ごとか

総合評価は、目的が変わると使えなくなる。美品を探す日と、安い掘り出し物を探す日では、見に行く出品者が違う。
[出品者探索 §12.5](../product/seller-discovery-spec.md#125-4つの山)で、Tabの名前を判断（候補）から事実（混ざっている）へ直したのと同じ理由である。

軸は3つ、段階は3つにとどめた。軸が多いと付けなくなり、段階が細かいと「3か4か」で止まる。
**3つと3段階は置いた値である**（[出品者探索 §11](../product/seller-discovery-spec.md#11-使ってみて見直すもの)）。

#### 評価は古くなる

**Aの「古くならない」は、評価については成り立たない。**出品頻度は、引退して出し切れば変わる。
ただし、古くなるのは読み手自身の見立てであって、Mercariの事実の写しではない。写しなら「今はどうか」を
取り直す責任が生じるが、見立てにそれは無い。**評価した日時を保存し、画面に出す。**いつの見立てかを読み手が見て、直す。

#### 買う前の見立てと、買った後の実績

ここで保存するのは、**見に行く優先度を決めるための見立て**である。届いたカードが申告どおりだったか、という
実績は別のもので、同じ欄に混ぜると何の評価かが分からなくなる。**実績の記録は、この決定に含めない**
（利用者が、あとで実装すると決めた。2026-11-20）。

#### ファイルの版

保存するFieldが増えたので、ファイルの`version`を2へ上げる（[論点2](#論点2--どこへどんな形で保存するか)）。

| 読む側 | 版1のファイル | 版2のファイル |
|---|---|---|
| この変更より後のCard Digger | 読める。評価は未評価として扱い、次に書くとき版2になる | 読める |
| この変更より前のCard Digger | 読める | **読めない。**Errorを出し、書き換えない |

**前の版へ戻したとき、評価を黙って捨てない。**版を上げずにFieldだけ足すと、前の版は評価を読み飛ばし、
次に書いたときに消す。読めないと言って止まるほうを選ぶ。

## 論点2 — どこへ、どんな形で保存するか

**利用者が決めたのは「Backendのローカルファイルへ保存する」までである。**形式と置き場所は実装者が選んだ。

### 形式

| | A. JSONファイル1つ | B. SQLite |
|---|---|---|
| 依存 | **無い。**標準ライブラリだけ | 無い（標準ライブラリにある） |
| 読み手が直接見られるか | **見られる。**Text Editorで開ける | 専用の道具が要る |
| 問い合わせ | できない。**毎回ぜんぶ読む** | できる |
| 壊れたとき | 何が書いてあるか読める | 読めない |

**Aを選んだ。**利用者は1人、件数は多くても数百で、**どの画面も一覧をまるごと読む。**
問い合わせが要る場面が無い。商品や調べた結果を保存し始めるなら（論点1のC）、そのときSQLiteへ移す。

### 置き場所

| | A. 環境変数で指定、既定はHome Directory | B. Repositoryの中（`src/backend/data/`など） |
|---|---|---|
| デプロイで消えるか | **消えない** | **消える。**[ADR 0003](0003-deploy-changes-to-the-target.md)は版ごとにDirectoryを作り、`current`を差し替える |
| [architecture §8](../development/architecture.md#8-デプロイ先をソースコードに持たない2026-11-08決定)との関係 | **合う。**置き場所はデプロイ先が設定で渡す | 反する。Repositoryの構成からPathを計算することになる |

**Aを選んだ。**

| 項目 | 値 |
|---|---|
| 環境変数 | `CARD_DIGGER_DATA_DIR`（Directoryを指す） |
| 未設定のとき | Home Directoryの`.card-digger/` |
| ファイル名 | `seller-lists.json` |

**家のWindowsでは設定を足さなくてよい。**未設定ならHome Directoryに置かれ、
版のDirectoryの外なので、デプロイしても残る。

### 書き込みの約束

| 約束 | 理由 |
|---|---|
| **隣に書いてから、名前を付け替える** | デプロイはProcessを止める。書き込みの途中で止まっても、古い一覧か新しい一覧のどちらかが残る |
| **読めないファイルを、空の一覧として扱わない** | 空として扱うと、次の保存が**その空を上書きする。**読み手が溜めた一覧が1件に置き換わる。Errorにして、ファイルには触らない |
| **使うまでディスクに触らない** | 一覧を一度も聞かない起動（Testの大半）が、Directoryを作らないようにする |

## 論点3 — 除外した出品者を、どこで検索結果から外すか

### 選択肢

| | A. Frontendで外し、件数を出す | B. Backendが外して返す |
|---|---|---|
| `POST /api/search`の応答 | **取得した範囲のすべて**（今のまま） | 除外後 |
| 何件外したかを画面に出せるか | **出せる。**外したものも手元にある | 件数を別に返せば出せる。**中身は見られない** |
| 外したものを見直せるか | **見直せる。**再取得なしで表示へ戻せる | 再検索が要る |

### 決定 — A

**[O-7](../planning/todo.md#オプション--判断済みで保留しているもの)が語彙による除外を保留した理由は
「削った先に何があったか永久に分からない」だった。**Aはその理由に当たらない。
外した出品者の出品は手元にあり、**何人・何件を出していないかを常に表示し、押せば表示へ戻る。**

`SearchResponse`の「取得した範囲のすべてを、並べ替えも絞り込みもせずに返す」という約束も変わらない。

## 変わらないもの

| 約束 | 状態 |
|---|---|
| **Databaseを持たない** | 変わらない。ファイル1つである |
| **認証を持たない** | 変わらない。リストの読み書きも、入口の認証に守られる（[architecture §8.2](../development/architecture.md#82-アプリがデプロイ先に求めること契約)） |
| **商品・Seller情報を保存しない** | 変わらない（論点1のA） |
| **検索・分析結果をCacheしない** | 変わらない。調べた結果は画面が開いているあいだだけ持つ |
| **Mercariへは同時実行1・開始間隔2秒以上** | 変わらない。リストの読み書きはMercariへ出ない |
| **uvicornは1 Process** | 変わらない。**ファイルを書くのが1 Processであることにも、この前提を使っている** |

- 論点1のAで、名前が出ないことが実用に耐えるかを、使って確かめる
