## 1. この画面が引き受けるもの

> **取得済みの商品1件について、買うかどうかを決めるために要るものを1か所に集める。**

### 一覧と役割を分ける

| 画面 | 引き受ける問い | 名前 |
|---|---|---|
| [検索画面](mvp-spec.md#5-検索画面) | **見る価値があるか** | **A（明らかな地雷を踏まない）** |
| **商品画面** | **買うか** | **B（見逃さない）** |

**一覧が絞れていないと、この画面がいくら良くても
[§20](concept.md#20-効率的かは利用者にしか答えられない2026-09-05決定)に負ける。**
50件開くなら、重い画面は毒である。この画面は**漏斗の最後**であって、閲覧面ではない。

### なぜ速くなるのか

**買う操作はCard Diggerに無い。** 買うにはMercariへ行く。**それでも往復は減る。**

| | 今 | この画面ができた後 |
|---|---|---|
| **見送る商品** | **Mercariを開いて、写真を見て、戻る** | **開かない** |
| 買う商品 | Mercariを開く | Mercariを開く |

**消えるのは「見送るために開いた往復」である。**
[実測](../../poc/mercapi/photos-result.md)では、Mercariの商品ページは`load`まで**1,796ms**
（写真を探して開く時間を含まない**下限**）、詳細1 Requestは**243ms**だった。

### やらないこと

| やらない | 理由 |
|---|---|
| **一覧の全Cardへ複数枚出す** | 120件ぶんの詳細で**240秒**。検索1回20〜30秒の10倍（[実測](../../poc/mercapi/photos-result.md#51-一覧で全cardに複数枚出すのは成立しない)） |
| **画像解析** | この用途では要らない。人が写真を見れば2秒で終わる |
| **この画面から買う・入札する** | [MVP仕様 §4](mvp-spec.md#4-mvpに含めない機能)と同じ。最終判断も購入もMercariで行う |
| **相場を計算する** | [§19](concept.md#19-相場データはcard-diggerが持たない2026-09-05決定)。受け取って表示する側になる |

## 2. 名前

**`商品画面`はCard Diggerの画面、`商品ページ`はMercariのページ、`商品詳細`はMercariのAPI。**
3つは別物で、**混ぜると仕様が読めなくなる。**

| 語 | 何を指すか | 出所 |
|---|---|---|
| **`商品画面`** | **この画面** | 2026-09-05に決めた。それまで使用0件 |
| `商品ページ` | **Mercariのページ。**画面の文言にも出ている | 既存（`Mercariの商品ページには表示されない値です`） |
| `商品詳細` | **MercariのAPI** | 既存（[§4](mvp-spec.md#4-mvpに含めない機能)「検索結果に対して詳細APIを呼ばない」） |
| `商品Card` | 検索結果の1枚 | 既存（[§5.6](mvp-spec.md#56-商品card)） |

**`◯◯画面`＝Card Digger、`◯◯ページ`＝Mercari**という区別は、
`Seller画面`と`Sellerページ`で既に成立している。**新しい規則ではない。**

## 3. 画面は4段でできている

| 段 | 出すもの | どこから | この着手 |
|---|---|---|---|
| **1** | **写真（全枚数）** | Mercari商品詳細 **1 Request** | **含める** |
| **2** | **説明文** | **同じ1 Request** | **含める。**追加Request **0** |
| 3 | 相場 | card-pulse | **含めない。**入る場所だけ決める |
| 4 | 束の推定総額 | [Phase 2](../planning/todo.md#実装--測定と決定の後) + Phase 3 | 含めない |

### 段3を含めない理由

**card-pulseは[§19](concept.md#連携の形はまだ決めていない)の時点で構想・調査文書だけの段階**で、
API・スキーマ・どちらが呼ぶかが未定である。**まだ無いものに合わせて作ると空振りする。**

**空の枠も出さない。** 「準備中」は利用者に何も与えず場所だけ取る。
**決めるのは位置だけ**で、コンポーネントは作らない。

### 段4は別の問いである

**まとめ売りに「相場」を1個の数字で出せない。** 300枚の束の相場とは何かが決まらない。
[§19](concept.md#答えの無い問いが1つ残っている)が既に書いている。

> **このまとめ売り、5,000円は高いのか安いのか。**
> 答えるにはPhase 2（写真から枚数と種類）とcard-pulseの両方が要る。**片方だけでは答えにならない。**

**段3は「人が指定した1枚の相場」まで**であり、束の合計は段4になる。

## 4. 入り方と出方

### 入り方 — 商品Cardのタイトル

**商品Cardのタイトルの行き先を、Mercariから商品画面へ変える。**

| | 今 | 変更後 |
|---|---|---|
| **タイトル** | **Mercariの商品ページ（外部）** | **商品画面（内部）** |
| `Mercariで商品を見る` | Mercariの商品ページ | **そのまま** |
| `Sellerを分析` | Seller画面 | そのまま |

**今のCardには「開く＝Mercariへ出る」道しか無い。** それがこの着手で消そうとしている往復
そのものなので、**既定の行き先を内側へ向ける。** Mercariへの導線は残す——買うには要る。

**これは[MVP仕様 §5.6](mvp-spec.md#56-商品card)の変更にあたる。** 同じ変更であちらも直す。

### 出方 — 買うのはMercariでしかできない

画面の下に**Mercariの商品ページへの外部Link**を置く。
**この画面が「買える画面」に見えてはいけない。**

Seller画面への導線も置く。**同じSellerの他の出品を見るのは、この画面から続く判断である。**

### 戻ったとき

**検索結果は再取得しない。** [§5.2](mvp-spec.md#52-検索開始)がSeller画面へ課しているのと同じ約束で、
結果・Sort・Filterは[SearchProvider](../development/architecture.md#2-層と依存の向き)が持っている。

**商品画面そのものは、開くたびに取得する**（[§6](#6-取得)）。

## 5. 表示内容

### 5.1 写真 — 全枚数

- 詳細が返した**全枚数**を出す。**先頭1枚は商品Cardと同じ画像**
- **枚数の上限を仕様に書かない。** 観測した最大は9枚で、Mercariの上限は確かめていない
- `loading="lazy"`を維持する。[実測](../../poc/mercapi/photos-result.md#44-描画は枚数を増やしても壊れない)が
  その条件で測っており、外すと測った値と別のものになる

**見え方（並べ方・大きさ・拡大の有無）は[視覚方針](design-tokens.md)が持つ。**

実測（[観測結果](../../poc/mercapi/photos-result.md#43-画像は状態を判断できる大きさだった)）。

| 指標 | 値 |
|---|---|
| 枚数 | 中央値**2**、最大**9** |
| 幅 | **1,080px**（最小810） |
| 1枚あたり | 約**177KB**、JPEG |

**「枚数はあるが小さすぎて状態が見えない」落とし穴は無かった。**

### 5.2 写真が1枚だけのとき（実測で3割）

> **写真はこの1枚だけです**

**エラーではない。出品者が1枚しか載せていない。**
[実測](../../poc/mercapi/photos-result.md#42-商品詳細は複数枚返すが3割は1枚のまま)では
**20件中6件**がこれだった。

**これを出す価値は「Mercariを開いても増えない」と言えることにある。**
開く価値が無いと分かるので、往復が1回減る。**この画面がいちばん安く効く場面である。**

`Mercariの商品ページには表示されない値です`と同じで、**転記であって主張ではない**
（[Adapter仕様 §6.3](../phase-0/phase-0-f-adapter-spec.md#63-field対応表--どこから来て意味に根拠があるか)）。

### 5.3 説明文

- 詳細Responseの`description`をそのまま出す。**要約しない。加工しない**
- **長さで畳まない。**「レアは抜いてあります」が畳まれた先にあると、この画面の意味が無くなる
- **検索結果とSeller商品一覧には`description`が無い。** 商品画面だけが持つ

**追加Requestは0である。** 写真と同じ1 Requestで来る。

### 5.4 一覧と同じ値をもう一度出す

**価格・商品の状態・掲載日・更新日時・販売形式**を出す。商品Cardと同じ値である。

**同じ判断を2か所に置くことにはならない。** これらは事実の転記であって判断ではない。
判断（Sort・Filter・Seller Knowledge）は一覧側にあり、ここへは来ない。

各値の断り書きは[§5.6](mvp-spec.md#56-商品card)と同じものを付ける。

**[未更新期間の棒](mvp-spec.md#未更新期間の棒2026-09-02決定)は出さない。**
棒は**Gridの中で隣と較べる**ための量で、1件だけの画面には較べる相手がいない。
Seller画面に出していないのと同じ理由である。

### 5.5 段3が入る場所

**説明文の下、Mercariへの外部Linkの上。**

読む順が判断の順になる。

```text
写真      → どんな状態か
説明文    → 何が入っていると書いてあるか
（段3 相場）→ いくらの価値か
価格      → 釣り合うか
Mercariへ → 買う
```

**位置だけ決める。今は何も出さない。**

## 6. 取得

### 6.1 開くたびに1 Request

**Seller画面と同じ形にする。** [`useSellerAnalysis`](../../src/frontend/src/useSellerAnalysis.ts)が
Route-localである理由がそのまま当てはまる。

> Hoisting it above the router would turn every return trip into a cache nobody asked for.

| 問い | 決めたこと |
|---|---|
| いつ取るか | **画面を開いたとき**と、Browserの再読み込み |
| 戻って再度開いたら | **もう一度取る** |
| 同じ商品を覚えておくか | **覚えない。**それはCacheであり、[O-5](../planning/todo.md#オプション--判断済みで保留しているもの)で保留した判断を崩す |
| 二重取得 | **させない。**`useSellerAnalysis`と同じく**Requestそのものを保持**する（Reactの二重mountで2秒を2回払わないため） |

### 6.2 状態の寿命

**Route-localに置く。** [アーキテクチャ §2.2](../development/architecture.md#2-層と依存の向き)の
「状態の寿命は、それが何についての事実かで決まる」に従う。

| 状態 | 何についての事実か | 置き場所 |
|---|---|---|
| 検索結果・Sort・Filter | **見ている結果**についての事実 | Providerの上（既存） |
| **商品画面の1件** | **この訪問**についての事実 | **Route-local** |

### 6.3 Requestの数と経路

| | 値 |
|---|---|
| 1回の表示につき | **Mercari API 1回**（商品詳細） |
| 画像 | **Browserが直接CDNから。**Backendは画像を取らない |
| 経路 | `MarketplacePort.get_item` → `RequestGate`（`Operation.ITEM`） |

**`get_item`も`Operation.ITEM`も既にある。**
Seller画面が[「非アクティブ」](mvp-spec.md#非アクティブを出す2026-09-05決定)のために
既に同じ経路を通っている。**[2秒間隔と安全停止](../development/architecture.md#41-外部アクセスの条件と2秒間隔の出所)は
新しく作らない。**

**2秒間隔は「前のRequestからの間隔」であって、1回の所要ではない。**
1件ずつ開く限り体感は実測の243msで、連続で開けば2秒待つ。

## 7. UI状態とError表示

**[§9](mvp-spec.md#9-ui状態とerror表示)の規則をこの画面へ写す。複製ではなく、当てはめである。**

| 状態 | この画面 |
|---|---|
| 初期 | **無い。**開いた瞬間に取得が始まる（Seller画面と同じ） |
| 取得中 | **`商品を取得中`** |
| 成功 | §5のとおり表示する |
| 0件 | **無い。**1件を指定して開くので、無ければ「見つからない」になる |
| 部分成功 | **無い。**1 Requestなので、成功か失敗しかない |
| 外部Error | §9の分類に応じた説明と、手動の再実行Button |
| 安全停止 | 自動再試行せず、**あと何秒で再試行できるか**を表示。**`Mercariへは問い合わせていません`**（[§9](mvp-spec.md#届かなかったことを画面が言う2026-09-05決定)） |

### 再実行Buttonの動詞

**`取得をやり直す`。** [§9の規則](mvp-spec.md#再実行buttonはその画面が使った動詞で名乗る2026-09-05決定)は
「その画面が使った動詞で名乗る」で、この画面が使う語は**取得**である（`商品を取得中`）。

Seller画面と同じ文字列になるが、**共通Componentが決めたからではない。**
両方が同じ動詞を使っているからである。

## 8. この画面が満たす受入条件

- [ ] 商品Cardのタイトルから商品画面が開き、**Mercariへ出ない**
- [ ] 詳細が返した**全枚数**の写真が出る
- [ ] **写真が1枚だけの出品で、`写真はこの1枚だけです`が出る**
- [ ] 説明文が**畳まれず・要約されず**に出る
- [ ] 1回の表示で**Mercariへのbackend Requestが1回**を超えない
- [ ] 商品画面から検索結果へ戻ったとき、**再検索が起きない**
- [ ] 取得中・失敗・安全停止が§9のとおり出る。**安全停止でMercariへ出ていないことが画面に出る**
- [ ] 主要操作がKeyboardとMobile Layoutで利用できる
- [ ] **相場・推定総額・カード同定が実装へ混入していない**
- [ ] **人間が見る商品を効率的に絞れるようになったか** — 利用者が答える。
  答えと一緒に、**まだ遅かったことを1行残す**
  （[§20](concept.md#20-効率的かは利用者にしか答えられない2026-09-05決定)）

**最後の1件だけは機械が判定できない。** 開発者側で`[x]`を入れない。
