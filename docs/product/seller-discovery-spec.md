## 1. 目的

**価値を分からずに出している出品者を、1人ずつ手で開かずに見つける。**

2026-11-19に利用者がMercariを巡回して、探したい出品者を次の2軸で述べた。

| 軸 | 利用者の言葉 | この仕様での呼び名 |
|---|---|---|
| 1 | ポケカだけでなく、**服や生活用品なども出品している** | **出品の幅**（[§3](#3-出品の幅)） |
| 2 | **美品を出品している** | **商品の状態**（[§5.2](#52-商品の状態は検索が既に持っている)） |

MVPのSeller画面は、同じ問いに**1人ずつ**答える。Seller Knowledgeは「詳しそうか」を出すので、
向きを逆に読めば軸1になる。**足りなかったのは、検索結果に出てきた全員を並べて比べる場所である。**

```text
検索する
    ↓
「出品者」Tabで、結果に出品していた人を並べる        ← 追加のRequestなし
    ↓
ボタンを押して、まだ調べていない人を調べる            ← 1人あたりMercariへ3回
    ↓
出品の幅・商品の状態・評価を見て、並べ替える
    ↓
保存する / 除外する                                   ← Mercariへ出ない
    ↓
次の検索では、除外した人の出品を出さない。保存した人は一覧から開ける
```

**購入の判断はしない。**どの出品者から見るかの順番を決める補助である。
これは[Seller Knowledge](mvp-spec.md#7-seller-knowledge-indicator)と同じ立場である。

## 2. 範囲

### 含める

- 検索結果を「商品」と「出品者」の2つのTabで見る
- 検索結果に出品していた出品者の一覧（一致した出品の件数、商品の状態）
- 出品者を順に調べる操作（名前、評価の内訳、出品の幅）
- 出品者の並べ替え（4種類）
- 出品者を保存リスト / 除外リストへ入れる、移す、外す、メモを書く
- 出品者リスト画面（保存 / 除外のTab）
- 除外リストの出品者の出品を検索結果から外し、**何人・何件を外したかを表示する**
- Seller画面で、その出品者がどちらのリストにあるかを見て変える
- **複数のキーワードで検索し、見つかった出品者を調べるところまでを、1回の押下で続けて行う画面**
  （「出品者検索」。[§12](#12-出品者検索2026-11-19追加)）
- **取得した結果を、タイトルに含む語で絞る**（[§13](#13-タイトルに含む語2026-11-19追加)）

### 含めない

| 含めないもの | 理由 |
|---|---|
| **出品者の名前・評価・調べた結果の保存** | [ADR 0004 論点1](../adr/0004-store-seller-lists-in-a-local-file.md#論点1--何を保存するか)。保存するのは読み手の決定だけ |
| **検索したときに自動で調べる** | 1人あたりMercariへ3回かかる。**押した人だけが、何回かかるかを見てから払う**（[§4](#4-出品者を調べる)）。「出品者検索」は検索と調べるを1回の押下で続けるが、**上限の回数を押す前に出し、検索画面の「検索」には何も足していない**（[§12.2](#122-押したときに起きること)） |
| **保存した出品者の新着を定期的に取りに行く** | [MVP仕様 §4](mvp-spec.md#4-mvpに含めない機能)の「定期検索、通知、Background Crawl」は対象外のまま |
| **出品の幅と商品の状態を1つの点数にまとめる** | 性質の違う主張である（[§5.3](#53-2つを1つにまとめない)） |
| **商品の状態を、出品者の全出品について集計する** | Seller商品一覧のResponseは状態を持たない（[MVP仕様 §5.6](mvp-spec.md#商品の状態2026-09-04決定)）。1件ずつ詳細を取ることになる |
| **画像からカードを判定する** | [Phase 2](../planning/todo.md#phase-2--画像解析)の範囲 |
| **Mercari上で出品者を検索する** | Mercariの出品者検索を使う経路を持っていない。**候補は、商品の検索結果から得る** |

## 3. 出品の幅

**出品のうち、TCG以外がどれだけあるか。**Seller Knowledgeと同じ標本を、逆向きに読む。

**画面には「カードの割合」として出す**（[§3.4](#34-画面にはカードの割合として出す2026-11-19に直した)）。
この節が定めるのはBackendが返す値で、帯（広い / 中 / 狭い）は画面に出していない。

### 3.1 計算

対象と正規化とTCG判定は、[MVP仕様 §7.1〜§7.4](mvp-spec.md#71-対象データ)をそのまま使う。

```text
otherItemCount = analyzedItemCount - tcgItemCount
otherRatio     = otherItemCount / analyzedItemCount
```

| TCG比率 | 出品の幅 | 表示 |
|---|---|---|
| 対象0件 | `unknown` | `判定不能` |
| 50%以上 | `narrow` | `狭い` |
| 20%以上50%未満 | `mixed` | `中` |
| 20%未満 | `wide` | `広い` |

### 3.2 閾値の出所

**新しい数字を足していない。**50%と20%は、[MVP仕様 §7.6](mvp-spec.md#76-比率とscore)が
TCG比率の加点に使っている2つの境界である。実装は定数を書き直さず、Seller Knowledgeの定義から読む。

**根拠の無い値を2つ増やさないためである。**Seller Knowledgeの閾値は「MVPの仮説」と明記してあり、
測った標本が無い。出品の幅だけ別の場所で切ると、**測らずに「幅は専門性と違う所で分かれる」と
決めたことになる。**

### 3.3 限界

| 限界 | 内容 |
|---|---|
| **Titleしか見ていない** | TCGの語を書かずにカードを出している出品は、TCG以外に数える。**この機能では、探したい側へ倒れる誤りである**（語を知らない出品者ほど「広い」になる） |
| **標本が小さい** | 調べるときは各状態1ページだけを取る（[§4.2](#42-1人あたり3回)）。件数を必ず帯の隣に出す |
| **閾値は仮説** | 上記のとおり |

**対象0件を`広い`にしない。**比率は`0.0`として返るが、これは「TCGを1件も出していない」ではなく
「何も分析できなかった」である。[MVP仕様 §7.7](mvp-spec.md#77-表示内容)の「対象0件のとき比率を出さない」と同じ扱いにする。

### 3.4 画面には「カードの割合」として出す（2026-11-19に直した）

**同じ2つの件数を、カードの側から言う。**

```text
Backendが返す    TCG以外 24件 / 53件
画面に出す       カードの割合 54.7%  カード 29件 / 53件
```

最初は、行に`出品の幅 狭い TCG以外 24件 / 53件（45.3%）`と出していた。
Tabを「カード専門」「混ざっている」に改めたあと（[§12.5](#125-4つの山)）、利用者が指摘した。

> カード専門と言っておきながら、45.3%と出ている。カード専門なら%が大きくならないとおかしい。

**45.3%は、カードではない側の割合だった。**Tabは「カードがどれだけあるか」で名前を付けたのに、
行は「カード以外がどれだけあるか」を出していた。読み手は%をカードの割合として読み、逆に受け取った。

帯の語（広い / 中 / 狭い）も出さない。「狭い」は幅の言い方で、カードの割合の隣では意味が通らない。
**出すのは割合と件数である。**帯にまとめると40%と45%が同じに見え、10%と40%が違って見える。

Backendの値と応答は変えていない。Frontendが`調べた件数 − TCG以外の件数`でカードの件数を出す。

**割合は実際より低めに出る。**カードかどうかはTitleの語で数えており（[§3.1](#31-計算)）、
カードの名前と型番だけを書いた出品は、カードでも数えない。断り書きにそう書く（[§5.6](#56-断り書き)）。

## 4. 出品者を調べる

### 4.1 押したときだけ調べる

**「出品者」Tabを開いても、Mercariへは何も送らない。**調べるのはボタンを押したときだけである。

理由は[O-8](../planning/todo.md#o-8--sellerの活動で検索結果を絞るのを打ち切った理由2026-09-04)と同じ計算である。
出品者1人を知るには1回以上の収集が要り、検索1回の時間に対して分単位が乗る。
**O-8はそれを検索のたびに自動で払うのを打ち切った。この仕様は、読み手が額を見てから払えるようにする。**

ボタンの隣に、必ず次を出す。

```text
[ まだ調べていない18人を調べる ]  Mercariへ54回問い合わせます（目安 約2分以上）
```

### 4.2 1人あたり3回

| Request | 取るもの |
|---|---|
| Seller Profile | 名前、評価の内訳、出品件数 |
| 販売中の1ページ目 | Title |
| 売却済みの1ページ目 | Title |

**Seller画面は1人に最大12回使う**（Profile 1、各状態で最大5ページ、商品詳細1）。
1人を選んで開くときは妥当だが、検索に出た全員へ掛けると、30人で最大12分になる。

| | Seller画面（`/analysis`） | 調べる（`/evaluation`） |
|---|---|---|
| ページ数（状態ごと） | 最大5 | **1** |
| 商品詳細（`非アクティブ`を読む） | 1回 | **取らない** |
| 応答に商品を含む | 含む | **含まない** |
| 最大Request数 | 12 | **3** |

**目安の時間は`人数 × 3回 × 2秒`で、下限である。**Requestそのものの時間が上に乗るので「以上」と書く。

### 4.3 順番と停止

- **1人ずつ順に調べる。同時には調べない。**Backendは元から同時実行1だが、
  画面から順に頼むことで、`止める`が「今の1人が終わったら止まる」になる
- **調べる順番は、検索結果に出た順である。**並べ替えを変えても、次に調べる人は変わらない。
  並べ替えは読み方であって、取得の順番を変える理由ではない
- **調べた人は、もう一度調べない。**ボタンは「まだ調べていない人」だけを対象にする

失敗したときの扱いは、**その失敗が誰についての事実か**で分ける。

| 失敗 | 何についての事実か | 扱い |
|---|---|---|
| 安全停止 | **Mercariについて**（こちらを拒んでいる） | **そこで止める。**残りは調べない。待ち時間を表示する |
| 429 | 同上 | **そこで止める** |
| Backendへ繋がらない | **Backendについて** | **そこで止める** |
| 404（出品者がいない） | **その出品者について** | 次へ進む。**二度と調べない**（同じ答えに1回使うだけになる） |
| Timeout、5xx、その他 | **その出品者についての1回** | 次へ進む。次に押したとき、もう一度調べる |

止まったときの文言と、再試行できるまでの待ちは、[MVP仕様 §9](mvp-spec.md#9-ui状態とerror表示)に従う。
**自動では再開しない。**

### 4.4 調べた結果の寿命

**画面を開いているあいだだけ持つ。保存しない。**

| 操作 | 調べた結果 |
|---|---|
| Seller画面へ行って戻る | **残る** |
| もう一度検索する | **残る。**同じ出品者が出れば、調べ済みとして表示する |
| Browserを再読み込みする | **消える** |

各行に、調べた時刻を出す。[MVP仕様 §5.2](mvp-spec.md#52-検索開始)の検索結果と同じ扱いであり、
期限も再検証も持たない。**Cacheではない。**

## 5. 「出品者」Tab

### 5.1 検索結果を2つのTabで見る

検索が1件以上を返したとき、[取得範囲の記録](mvp-spec.md#54-検索結果metadata)の下に2つのTabを置く。

| Tab | 中身 | 件数 |
|---|---|---|
| `商品` | SortとFilter、商品Card（MVPのまま） | 条件に一致した商品の数 |
| `出品者` | この節の一覧 | 出品者の人数 |

**取得範囲の記録はTabの外に置く。**どちらのTabを見ていても「取れた範囲」であることは変わらない。

**開いていたTabは、Seller画面から戻っても同じである。**

### 5.2 商品の状態は、検索が既に持っている

出品者ごとに、**その検索で一致した出品**について次を出す。追加のRequestは要らない。

| 項目 | 内容 |
|---|---|
| 一致した出品 | 件数 |
| 一致した出品の状態 | Mercariの表示名ごとの件数。良い順。例: `目立った傷や汚れなし 2件、不明 1件` |

**出品者の全出品ではなく、検索に出た出品の状態である。**画面にそう書く。

**`不明`を悪い状態として数えない。**並べ替えでも最後に置くだけで、傷ありより下とは扱わない
（[MVP仕様 §5.5](mvp-spec.md#状態不明を落とさない)と同じ）。

### 5.3 2つを1つにまとめない

出品の幅と商品の状態を、**別々の項目として出す。点数にしない。**

| | 出品の幅 | 商品の状態 |
|---|---|---|
| 誰が言ったか | Card Diggerが、Titleから数えた | **出品者が、自分で選んだ** |
| 範囲 | 各状態1ページの出品 | 検索に出た出品だけ |
| 疑うべき点 | 標本が小さい。閾値が仮説 | **基準が人によって違う。**実物を見ていない |

1つの数字にすると、**どちらを疑うべきかが読めなくなる。**
[MVP仕様 §7.7](mvp-spec.md#77-表示内容)が専門性と標本信頼度を分けているのと同じ理由である。

### 5.4 1行に出すもの

| 塊 | 項目 |
|---|---|
| 誰か | 名前（調べる前は`Seller <ID>`）。**名前はMercariの出品者ページへのLink**（別のTab）。一致した出品のうち最初の1件のTitle。その下に`Sellerを分析`（Seller画面へのLink） |
| 分かったこと | 一致した出品、一致した出品の状態、カードの割合（`P%` + `カード N件 / M件`。[§3.4](#34-画面にはカードの割合として出す2026-11-19に直した)）、評価の内訳 |
| どうするか | `保存する` / `除外する`、または`移す` / `外す`。調べた時刻 |

**名前を押すと、Mercariの出品者ページが開く。Seller画面は開かない**（2026-11-19に直した）。
最初は名前がSeller画面へのLinkだった。Seller画面は開いた時点で収集を始めるので
（[§4.2](#42-1人あたり3回)。最大12回）、**名前を押しただけでMercariへ最大12回問い合わせていた。**
利用者が「名前を押したら、Mercariの出品者のページへ飛ぶほうが良い」と言った。

| 押すもの | 行き先 | Card DiggerからMercariへの問い合わせ |
|---|---|---|
| 名前 | Mercariの出品者ページ（別のTab） | **0回** |
| `Sellerを分析` | Seller画面 | 最大12回 |

Seller画面への道は残す。商品Cardと同じ`Sellerを分析`という語で、名前の下に置く
（[MVP仕様 §5.6](mvp-spec.md#56-商品card)）。[MVP仕様 §6.1](mvp-spec.md#61-取得開始)は、
Seller画面が取得を始めるのを「`Sellerを分析`から遷移したとき」と定めている。
**名前からSeller画面へ行けた最初の形は、その語を押していない人にも取得を始めさせていた。**
調べる前の出品者にもLinkを出す。行き先はSeller IDから組み立てられ、調べるのを待つ理由が無い。

**出品者リスト画面の名前は、Seller画面へのLinkのままである**（[§6.2](#62-画面)）。利用者が指したのは
検索結果と「出品者検索」の行で、そちらだけを直した。

**商品の状態のラベルは`一致した出品の状態`と書く。**カードの割合と評価は出品者についての項目だが、
商品の状態は「一致した出品」についての項目であり、出品者の性質ではない（[§5.2](#52-商品の状態は検索が既に持っている)）。
`商品の状態`とだけ書いて4つを並べていたところ、利用者が「これだけ商品単体の性質で、分かりづらい」と指摘した（2026-11-19）。

```text
一致した出品        2件
一致した出品の状態  目立った傷や汚れなし 2件
カードの割合        9.1%  カード 2件 / 22件
評価                良い 310・普通 4・悪い 0
```

**段を下げて件数の内訳にする案は採らなかった。**試したところ、利用者が「元の並びのほうが分かりやすい」と答えた（同日）。
4つを同じ段に並べたまま、名前で区別する。

**カードの割合は、%だけを出さない。件数を必ず添える。**`100%`が3件から出たのか60件から出たのかで、
同じ帯が別の主張になる。

調べる前のカードの割合は`未調査`、順番待ちは`順番待ち`、失敗は`取得できませんでした`、調べたが出品が無いときは`判定不能`、
出品者がいないときは`この出品者は見つかりませんでした`と出す。

### 5.5 並べ替え

| 並び順 | 規則 |
|---|---|
| `検索結果に出た順`（初期） | 検索結果で最初に現れた順 |
| `カードの割合が低い順` | カードの割合が低い出品者から → 判定不能 → まだ調べていない。**帯ではなく割合そのもので並べる** |
| `一致した出品の状態が良い順` | **いちばん傷んだ出品**が、より良い出品者から。状態が分からない出品者は最後 |
| `一致した出品が多い順` | 件数の多い順 |

どの並び順も、同じなら検索結果に出た順へ戻る。**調べる前に「カードの割合が低い順」を選んでも、並びは変わらない。**
何も分かっていないのに並びが動くと、何かが見つかったように読める。

「一致した出品の状態が良い順」を最悪の1件で決めるのは、**良いカードを1枚出している人と、
良いカードを出す人は違う**からである。

### 5.6 断り書き

一覧の下に、朱の縦罫で次を出す（[視覚方針 §3.3](design-tokens.md#33-朱は1つの意味しか持たない--partialtrueの警告色)）。

```text
「一致した出品」と「一致した出品の状態」は、この検索で取得した出品についてのものです。
出品者の出品全体の状態ではありません。
商品の状態は出品者が選んだ区分であり、実物を確認したものではありません。
「カードの割合」は、販売中と売却済みそれぞれ最初の1ページのTitleから数えています。
Titleにカードの語（ポケカ、トレカ、遊戯王など）が無い出品は、カードでも数えないので、実際より低めに出ます。
閾値は仮説であり、精度を実証した値ではありません。
購入判断ではなく、確認順を決める補助情報です。
```

## 6. 出品者リスト

### 6.1 保存するもの

[ADR 0004 論点1](../adr/0004-store-seller-lists-in-a-local-file.md#論点1--何を保存するか)が正本である。
Seller ID、リストの種別、追加した日時、読み手のメモだけを保存する。

| 規則 | 内容 |
|---|---|
| 1人は、どちらか1つのリストにだけ入る | 入れ直すと、前の登録を置き換える。両方に入っている瞬間は無い |
| メモは200字まで | 前後と途中の空白を詰めてから数える。改行は空白になる |
| **メモを書き直しても、追加した日は変わらない** | 追加した日は「いつから見ているか」である |
| **別のリストへ移すと、追加した日はその時刻になる** | 新しい決定である。メモは持っていく |
| リストに無い出品者を外しても、Errorにしない | 頼まれたのは「入っていないこと」であり、そうなっている |

**リストの操作は、Mercariへ何も送らない。**安全停止の最中でも使える。

### 6.2 画面

画面上部に行き先を2つ置く。`検索`と`出品者リスト`（登録した人数を添える）。

出品者リスト画面は、`保存`と`除外`を**Tabで分け、片方ずつ出す。**
逆の決定を1つの列に並べると、取り違えて操作する。

| 項目 | 内容 |
|---|---|
| 出品者 | `Seller <ID>`。Seller画面へのLink。**画面を開いてから調べた出品者だけ、名前を出す** |
| 追加した日 | 日付（Asia/Tokyo） |
| メモ | 入力欄と`メモを保存`。変更が無いあいだは押せない |
| 操作 | `保存へ移す` / `除外へ移す`、`外す` |

並びは新しく追加した順とする。

**名前が出ないことを、画面に断る。**

```text
保存しているのは、Seller ID、どちらのリストか、追加した日、メモだけです。
出品者の名前・評価・商品は保存していません。
名前は、この画面を開いてから調べた出品者についてだけ表示されます。
```

### 6.3 Seller画面

Profileの直下に、その出品者がどちらのリストにあるかを出す。入っていればメモを書けて、移す・外すができる。
入っていなければ`保存する`と`除外する`を出す。

### 6.4 一覧を読めないとき

| 状態 | 表示 |
|---|---|
| 読み込み中 | リストの操作を押せなくする。**どちらのリストにあるか分からないまま`保存する`を出すと、除外した人を保存へ動かせてしまう** |
| 読めなかった | `出品者リストを読み込めませんでした`と`読み込み直す` |
| 変更を保存できなかった | `出品者リストを保存できませんでした。リストは変更されていません`。**Mercariのせいにしない** |

## 7. 検索結果からの除外

**除外リストの出品者の出品を、検索結果の両方のTabから外す。**

| 規則 | 内容 |
|---|---|
| 外す場所 | **Frontend。**`POST /api/search`の応答は変えない（[ADR 0004 論点3](../adr/0004-store-seller-lists-in-a-local-file.md#論点3--除外した出品者をどこで検索結果から外すか)） |
| 順番 | **除外が先、Filterが後。**商品Tabの件数は両方を通った数である |
| 取得範囲の記録 | **変えない。**記録は取得について述べるもので、表示について述べるものではない |
| 表示 | 外したものが1件でもあれば、Tabの上に人数と件数を出す |
| 戻す | `表示する`を押すと、除外リストの出品者も表示する。**再取得しない** |

```text
除外リストの出品者 2人・5件を表示していません  [ 表示する ]
除外リストの出品者 2人・5件を含めて表示しています  [ 隠す ]
```

**数えるのは、その検索結果に出ていた出品者だけである。**除外リストに50人いても、
この結果に2人しか出ていなければ「2人」と出す。**1人も出ていなければ、何も出さない。**

これは断り書きではなく、**読み手が自分で決めたことの確認**である。朱の縦罫は使わない。

## 8. Backend API

[MVP仕様 §8](mvp-spec.md#8-backend-api)のStatus規則に、次を足す。

### `GET /api/sellers/{sellerId}/evaluation`

Seller Profile、Seller Knowledge、出品の幅、各状態の`CollectionMeta`を返す。**商品は返さない。**

```json
{
  "seller": { "id": "…", "name": "…", "ratingBreakdown": { "good": 310, "normal": 4, "bad": 0 } },
  "knowledge": { "analyzedItemCount": 22, "tcgItemCount": 2 },
  "breadth": { "analyzedItemCount": 22, "otherItemCount": 20, "otherRatio": 0.909, "level": "wide" },
  "onSaleMeta": { "stopReason": "max_pages", "truncated": true },
  "soldOutMeta": { "stopReason": "end_of_results", "reachedEnd": true }
}
```

- Statusは`GET /api/sellers/{sellerId}/analysis`と同じ規則に従う
- `truncated: true`は故障ではない。**1ページで止めた**ことの申告である
- 同じ出品者の`/analysis`とは**別の収集**として扱い、片方がもう片方の結果を受け取らない

### `GET /api/seller-lists`

両方のリストを1つの配列で返す。追加した日の古い順。**Mercariへ通信しない。**

```json
{ "entries": [ { "sellerId": "100000001", "kind": "saved", "addedAt": "2026-11-19T03:00:00Z", "note": "" } ] }
```

### `PUT /api/seller-lists/{sellerId}`

```json
{ "kind": "saved", "note": "服も出品している" }
```

出品者をリストへ入れ、**変更後の両方のリストを返す。**`note`は省略できる。

### `DELETE /api/seller-lists/{sellerId}`

出品者をリストから外し、**変更後の両方のリストを返す。**入っていなくても200を返す。

### Status

| 条件 | Status | 本体 |
|---|---:|---|
| 成功 | 200 | 両方のリスト |
| `kind`が`saved` / `excluded`以外 | 422 | FastAPIのValidation |
| Seller IDが空・空白を含む・64字超 | 422 | `{ "detail": { "code": "invalid_input", "field": "sellerId" } }` |
| メモが200字超 | 422 | `{ "detail": { "code": "invalid_input", "field": "note" } }` |
| ファイルを読めない・書けない | **500** | `{ "detail": { "code": "seller_lists_unavailable" } }` |

**500は、Mercariの失敗に使うStatus（502 / 503 / 504）と重ならない。**
手元のファイルの故障を「Mercariが応答しなかった」と表示させないためである。
**Pathもファイルの中身も、応答に入れない。**

## 9. Test

どうTestするかは[Test運用規約](../development/test-policy.md)が持つ。ここは**何をTestするか**である。

### Backend

- 出品の幅が50%と20%で切れること。境界は`以上`の側へ入ること
- 出品の幅の閾値が、Seller Knowledgeの定義と同じ値であること
- 対象0件が`unknown`であり、`wide`にならないこと
- `/evaluation`が**3 Request**で、商品詳細を取らず、2ページ目を追わないこと
- `/evaluation`の応答に商品が含まれないこと（Field名の集合で検査する）
- 連続3回の拒否が出品者をまたいで数えられ、4人目がMercariへ出ないこと
- `/evaluation`と`/analysis`が互いの結果を受け取らないこと
- リストの読み書きが`MarketplacePort`を1回も呼ばないこと
- リストの応答とファイルに、Seller ID・種別・日時・メモ以外が入らないこと（Field名の集合で検査する）
- メモの書き直しで追加した日が変わらず、移すと変わること
- 読めないファイルがErrorになり、**ファイルが書き換わらないこと**
- 起動しただけではDirectoryが作られないこと
- Memory実装とFile実装が同じ振る舞いをすること

### Frontend

- 「出品者」Tabを開いても`sellerEvaluation`が呼ばれないこと
- 押したとき、検索結果に出た順に、**1人ずつ**呼ばれること（前の応答を待つこと）
- 安全停止で止まり、残りが呼ばれず、`順番待ち`が残らないこと
- 1人の失敗で止まらず、その人が「まだ調べていない人」に残ること
- 404の出品者を二度と調べないこと
- `止める`が、今の1人のあとで止まること
- Seller画面から戻っても、調べた結果とTabが残り、再検索しないこと
- 調べる前に「幅が広い順」を選んでも並びが変わらないこと
- `不明`の状態を悪い状態として並べないこと
- 除外すると両方のTabから消え、人数と件数が出ること。`表示する`で戻り、再検索しないこと
- リストの変更に失敗したとき、文言がMercariに触れないこと

「出品者検索」（[§12](#12-出品者検索2026-11-19追加)）について。

- 画面を開いても、入力しても、`search`と`sellerEvaluation`が呼ばれないこと
- 押す前に上限の回数が出ており、キーワードの数と調べる人数に追従すること
- キーワードが0個、価格帯が逆のとき、何も送らずに断ること。6つ目の欄を足せないこと
- **1つの欄に書いた語を、分けて検索しないこと。**空白で区切っても、Enterを押しても、検索は1回であること
- 欄を2つ以上使うとき、別々に検索して合わせることを、押す前に文で出すこと
- キーワードを1つずつ順に検索すること（前の応答を待つこと）
- 2つのキーワードに一致した出品を、1件として数えること
- 一致した出品が少ない出品者から調べ、上限の人数で止まり、残した人数を表示すること
- もう一度押すと、残した人から調べ、同じ人を二度調べないこと
- 除外リストの出品者を調べず、人数と件数を表示すること
- 1つの検索の失敗で止まらず、安全停止では次の検索も出品者も呼ばないこと
- `止める`が、今の検索のあとで止まり、出品者を調べないこと
- 調べた出品が30件に満たない出品者が、「カード専門」に入らないこと
- まとめて除外するボタンが「カード専門」にだけあり、その人たちだけを除外すること
- Tabの名前が、出品者の棚について言う4つ（混ざっている / 出品が少ない / カード専門 / 未調査・不明）であること
- 行が**カードの割合**を出し、「TCG以外」の割合を出さないこと
- カードの割合80%で「カード専門」に入り、80%ちょうどが入ること。29件 / 53件（54.7%）が入らないこと
- 「カードの割合が低い順」が、帯ではなく割合そのもので並ぶこと
- 検索画面の状態を変えないこと

「検索」と「調べる」を分けたこと（[§15](#15-検索と調べるを別の押下にする2026-11-19追加)）について。

- 「検索」が出品者を1人も調べないこと。「調べる」が検索をやり直さないこと
- 「調べる」の前に、対象の人数と、実数の回数が出ること
- 語を変えても一覧が変わらず、「調べる」を押すと切り替わること
- 対象の全員が調べ済みのとき、「調べる」が何も送らずに一覧だけを切り替えること
- 出品者を調べているあいだ、語と人数を変えられないこと
- 新しく検索したあと、「調べる」を押すまで一覧を出さないこと
- 「取得する条件」に語と人数が無く、「調べる出品者」にあること。出品者検索に「表示の絞り込み」が無いこと

調べる順番と、結果の読み方（[§16](#16-調べる順番と結果の読み方2026-11-19追加)）について。

- 調べる順番の初期値が「少ない人から」で、「多い人から」を選ぶと逆になること。同数は見つかった順のままであること
- 対象が人数の上限に収まるとき、どちらの順でも同じ人を調べること
- 良い評価での絞り込みと並び順の変更が、何も送らないこと。戻すと全員が戻ること
- 評価の件数が分からない出品者を、良い評価での絞り込みで外さないこと
- 表示の塊に「タイトルに含む語」が無いこと
- 出品者を調べているあいだ、調べる順番も、表示の絞り込みも変えられないこと
- ほかの画面へ行って戻っても、表示の絞り込みと並び順が残っていること

「タイトルに含む語」（[§13](#13-タイトルに含む語2026-11-19追加)）について。

- 欄が空のとき、何も絞らないこと
- 語のどれか1つをタイトルに含む出品だけを残すこと。全部を求めないこと
- 全角 / 半角、大文字 / 小文字、ひらがな / カタカナを区別しないこと
- 検索画面の両方のTabから同じ出品が外れ、件数が出ること
- 欄を空にすると戻り、再検索しないこと。入力しても何も送らないこと
- 残る出品が1件も無い出品者だけを、人数に数えること
- 「出品者検索」で、外れた出品でしか見つからなかった出品者を調べないこと
- 欄を空にして戻った出品者を、調べに行かないこと
- 見つかった出品がすべて外れたとき、「見つからなかった」と出さないこと
- 2つの画面が同じ語を使うこと

`scripts/seller_discovery_demo.py`が、幅の違う出品者6人を持つBackendを起動する。**Mercariへは通信しない。**

```bash
cd src/backend && uv run uvicorn --factory scripts.seller_discovery_demo:create_seller_discovery_demo_app --reload
```

`ポケカ まとめ`で検索し、「出品者」Tabを開く。

**決めたのではなく、まず置いた値である。**

| 見直すもの | 今の値 | 見直すきっかけ |
|---|---|---|
| 出品者リストに名前が出ない | Seller IDとメモだけ | 一覧が読めない、と感じたとき（[ADR 0004 論点1](../adr/0004-store-seller-lists-in-a-local-file.md#分かっている代償)） |
| 出品の幅の閾値（Backendの帯） | 50% / 20% | 画面は帯を出していない（[§3.4](#34-画面にはカードの割合として出す2026-11-19に直した)）。帯を使う画面を足すとき |

| 調べる深さ | 各状態1ページ | 標本が小さすぎて帯が当てにならないとき |
| 「美品」の軸 | 検索に出た出品の、出品者が選んだ状態 | 状態の申告と実物のずれが、仕入れて分かったとき。**出品者ごとのずれを記録する場所は、まだ無い** |
| 保存した出品者の新着 | 1人ずつSeller画面で開く | 保存した人数が増え、開いて回るのが手間になったとき |
| 検索画面の縦の長さ | 取得範囲の記録がTabの上にある | 記録が長く、Tabまで遠いとき。**記録を畳むかは[MVP仕様 §5.4](mvp-spec.md#54-検索結果metadata)の変更になる** |
| 調べる順番 | 少ない人から / 多い人から。初期値は少ない人から | 多い人からにしても専門の人に当たらない、またはその逆のとき（[§16.1](#161-調べる順番)）。**どちらも測っていない** |
| 良い評価での絞り込み | 表示だけ。調べる途中では打ち切らない | 評価の少ない人が大半で、見る気も無い、と分かったとき（[§16.3](#163-調べる途中で打ち切らない)） |
| 「検索」と「調べる」を分けたこと | 2回押す | 押す回数が増えたのが手間で、1回で最後まで進めたいとき（[§15.5](#155-手放したもの)） |
| 「出品者検索」の上限 | キーワード5つ、出品者10 / 20 / 30人（既定20人） | 続けて押した最大の140回が拒否されたとき。逆に、30人では1回で集まる出品者が少なすぎるとき（[§12.3](#123-上限)） |
| 「出品者検索」で調べる順番 | 一致した出品が少ない出品者から | 探したい出品者が後ろに回っていた、と分かったとき（[§12.4](#124-誰から調べるか)）。**この順番は、Mercariが弱く一致させた出品の出品者を先頭に持ってくる**（[§13.1](#131-何が起きていたか)）。タイトルで絞っても先頭に関係の薄い人が並ぶなら、順番のほうを見直す |
| タイトルに含む語 | 毎回入力する。保存しない。既定は空欄 | 同じ語を毎回打ち直しているとき。説明文にしか書いていない出品を逃している、と分かったとき（[§13.6](#136-限界)） |
| 「出品が少ない」の線 | 調べた出品が30件未満 | 「出品が少ない」に専門の出品者が溜まる、または「カード専門」に個人が混ざるとき（[§12.5](#125-4つの山)） |
| 山の名前 | 混ざっている / 出品が少ない / カード専門 / 未調査・不明 | 名前から中身を取り違えたとき。**1度直している**（[§12.5](#125-4つの山)） |
| 探すキーワード | 毎回入力する。保存しない | 同じ語を毎回打ち直しているとき。**保存するなら[ADR 0004](../adr/0004-store-seller-lists-in-a-local-file.md)の範囲が変わる** |

## 12. 出品者検索（2026-11-19追加）

### 12.1 何のための画面か

**出品者を集める作業そのものを手伝う。**

[§5](#5-出品者tab)の「出品者」Tabは、検索した結果の出品者を見比べる画面である。
それを使って出品者を集めるには、キーワードごとに「検索する → Tabを開く → 調べるを押す → 読む」を繰り返す。
**利用者が欲しいと言ったのは、その繰り返し（収集）の手助けだった。**

この画面は、キーワードをまとめて受け取り、検索から出品者を調べるところまでを続けて行い、
結果を「出品にカードがどれだけあるか」で分けて出す。**数えているもの（Titleの語でカードかどうかを数える）は[§3](#3-出品の幅)のままで、
新しい指標は足していない。**Backendも変えていない（[§8](#8-backend-api)のEndpointだけを使う）。

画面は商品検索・出品者リストと並ぶ3つ目で、Pathは`/find-sellers`である。

**画面の名前は「出品者検索」である。**最初は「出品者を探す」だった。Menuの「検索」を「商品検索」に改めたのに合わせ、
揃えるかを利用者に尋ね、実装の指示を受けて揃えた（2026-11-19）。Buttonは当時「探す」1つだった（今は「検索」と「調べる」。[§15](#15-検索と調べるを別の押下にする2026-11-19追加)）。

**名前は出品者検索だが、Mercariの出品者検索を使うわけではない**（[§2](#含めない)。その経路を持っていない）。
商品を検索し、その結果に出品していた人を拾う。画面の最初の文にそう書く。

**Menuの「検索」は「商品検索」に改めた**（2026-11-19。利用者の指摘）。「出品者検索」が隣に並ぶと、
「検索」だけでは何を検索する画面か分からない。Seller画面の戻るLinkも「商品検索へ戻る」にした。

### 12.2 押したときに起きること

**押すものは2つある**（2026-11-19に、1つから2つへ分けた。[§15](#15-検索と調べるを別の押下にする2026-11-19追加)）。

```text
[検索]
  1. キーワードを上から1つずつ検索する（検索画面の「検索」と同じ収集。販売中、同じ価格帯）
  2. 見つかった出品を1つにまとめる（複数のキーワードに一致した出品は1件）

[調べる]
  3. 除外リストの出品者と、「タイトルに含む語」で外れた出品を外す
  4. 残った出品者を、選んだ人数まで1人ずつ調べる（§4と同じ3回）
  5. 調べた結果で4つの山に分ける
```

**画面を開いても、入力しても、Mercariへは何も送らない。送るのは、この2つを押したときだけである。**
[§4.1](#41-押したときだけ調べる)の「読み手が額を見てから払う」を、検索まで含めて守る。
それぞれのボタンの隣に、必ず回数を出す。入力に追従する。

```text
[ 検索 ]    Mercariへ最大30回問い合わせます（検索1回につき最大10回。上限まで使うと約1分以上）
[ 調べる ]  Mercariへ12回問い合わせます（4人 × 3回。約24秒以上）
```

**「検索」の回数は上限で、「調べる」の回数は実数である。**調べる時点では、誰を調べるかが決まっている。

### 12.2.1 欄1つが、検索1回（2026-11-19に直した）

**キーワードの欄は1つから始まる。**検索画面と同じ形で、`ポケモンカード 押入れ`と書けば、
検索画面でそう検索したときと同じ1回の検索になる。**1つの欄に書いた語を、分けて検索しない。**

2つ目の検索は、`別のキーワードでも探す`を押して欄を足したときだけ行う。欄ごとに別々に検索し、
見つかった出品を合わせる。**合わせるので、どれか1つの検索に一致すれば結果に入る。**
欄が2つ以上あるときは、そのことを欄の下に文で出す。

```text
欄が2つ以上  2つのキーワードは別々に検索し、見つかった出品を合わせます。
```

欄が1つのときは、何も足さない。最初は「1つの欄が1回の検索です」と書いていたが、
利用者が「要らない」と言った（2026-11-19）。欄が1つしか無ければ、検索が1回であることは言うまでもない。
欄の下には、キーワードがどこの一致を見ているかを書く（[§13.7](#137-キーワードの欄に書くこと)）。

**最初の実装は、1つの入力欄に「1行に1つ」書く形だった。これは誤りだった。**
利用者が`ポケモンカード`と`押入れ`で探したところ、説明文に「押入れ」とだけ書いてあるナルトカードの出品が出た。
2語が2行に分かれ、2回の検索になって合わさったためである。**検索画面で同じ語を検索すれば出ない出品が、
この画面では出る。**利用者が「意図した検索結果になっていない」と指摘した。

改行1つで「両方を含む」が「どちらかを含む」に変わり、しかも結果を見るまで分からない。
[§12.2](#122-押したときに起きること)の「読み手が額を見てから払う」は回数についての約束だが、
**何を検索するのかが押す前に分からなければ、回数だけ見せても足りない。**
欄を分け、足すのを操作にして、検索の数が画面の形から分かるようにした。Enterは検索を始める（欄を足さない）。

なお、Mercariが空白で区切った語をどこまで厳密に「両方を含む」として扱うかは、Card Diggerは確かめていない。
言えるのは「検索画面と同じ1回の検索になる」までである。

### 12.3 上限

| 上限 | 値 | 出所 |
|---|---|---|
| キーワード（欄の数） | **5つ** | **置いた値。**検索画面が例として出している語が5つである |
| 検索1回のページ数 | 10 | [MVP仕様 §5.3](mvp-spec.md#53-収集範囲)の値そのまま |
| 一度に調べる人数 | **10 / 20 / 30人から選ぶ。既定20人** | **置いた値** |
| 出品者1人 | 3回 | [§4.2](#42-1人あたり3回) |

押下ごとの上限は次のとおりである。

| 押すもの | 上限 | 最大 |
|---|---|---:|
| 検索 | `キーワード数 × 10`回 | 5語で50回 |
| 調べる | `人数 × 3`回 | 30人で90回 |

**どちらの押下も、単独では観測の範囲に収まる。続けて押すと、最大140回で超える。**
[architecture §4.1](../development/architecture.md#41-外部アクセスの条件と2秒間隔の出所)の「2秒間隔で拒否されなかった」は
L4の110〜123回での観測である。拒否されたときは安全停止が効く（[§12.8](#128-止まるとき)）。
**上限を広げる根拠にも、狭める根拠にもなる観測は、まだ無い。**

数え方について2点。

- **回数は「ページ」と「出品者」の数である。**Backendは一時的な失敗を1回だけやり直すので、その分は含まない。
  [§4.2](#42-1人あたり3回)の「3回」と同じ数え方である
- **時間は`回数 × 2秒`で、その回数を使ったときの下限である。**Requestそのものの時間が上に乗るので「以上」と書く

**検索の回数は、上限であって見積もりではない。**出品が尽きれば10ページより前に終わる。

### 12.4 誰から調べるか

**一致した出品が少ない出品者から調べる。**同数なら、見つかった順である。
逆の順（多い出品者から）も選べる（[§16.1](#161-調べる順番)）。初期値は少ない順のままである。

人数に上限があるので、誰が上限の内側に入るかで結果が変わる。
1回の検索に同じ人の出品がいくつも出るのは、大量に出品している人であることが多い。
[O-8の実測](../planning/todo.md#o-8--sellerの活動で検索結果を絞るのを打ち切った理由2026-09-04)では、
1,000件の検索結果にユニーク出品者が629人いて、2件以上出していたのは109人だった。
探しているのは残りの側（1件だけ出している人）に多い、という見立てである。

**見立てであって、測っていない。**[§11](#11-使ってみて見直すもの)に置いた。

[§4.3](#43-順番と停止)の「検索結果に出た順」と違うのは、上限の有無による。
「出品者」Tabは全員を調べる操作なので、順番は結果を変えない。こちらは変える。

調べる対象から外すもの。

| 外すもの | 理由 |
|---|---|
| 除外リストの出品者 | 読み手が既に「見ない」と決めている。**何人・何件を外したかを、「調べる出品者」の塊に出す** |
| 「タイトルに含む語」で外れた出品しか無い出品者 | [§13.4](#134-出品者検索では誰を調べるかを決める) |
| 既に調べた出品者 | [§4.4](#44-調べた結果の寿命)。「出品者」Tabで調べた人も含む。**上限の人数を使わない** |
| 404だった出品者 | [§4.3](#43-順番と停止)。二度と調べない |

**人数の上限に届いて調べなかった人数を、押す前にも後にも出す。もう一度「調べる」を押すと、残した人から調べる。**
検索はやり直さない。

### 12.5 4つの山

調べた結果を、Tabで4つに分ける。**最初に開くのは「混ざっている」である。**

| 山 | 入る出品者 | 根拠 |
|---|---|---|
| **混ざっている** | カードの割合が**80%未満** | カード以外も出品している |
| **出品が少ない** | カードの割合が80%以上で、**調べた出品が30件未満** | 下記 |
| **カード専門** | カードの割合が80%以上で、調べた出品が30件以上 | 8割以上がカードで、そう言えるだけの件数がある |
| **未調査・不明** | まだ調べていない、取得できなかった、出品が無く判定できなかった | 何も言えない |

#### 名前は、出品者の棚について言う。どうするかは言わない（2026-11-19に直した）

最初の名前は「候補」「少数出品」「専門らしい」「その他」だった。利用者が、分かりづらいと指摘した。

| 最初の名前 | 何が分からなかったか |
|---|---|
| 候補 | 何の候補なのか |
| 少数出品 | 何が少数なのか |
| 専門らしい | 何の専門なのか |

**3つとも、実装者の判断を名前にしていた。**「候補」は「カードの価値を知らない人を探す」という1つの使い方から見た評価であり、
出品者についての事実ではない。利用者は別の読み方を示した。

```text
美品のカードを探すとき          → カード専門を見る
掘り出し物、相場より安い商品を探すとき → 混ざっているを見る
```

**同じ山が、目的によって見に行く先にも、避ける先にもなる。**だから山の名前は「出品にカードがどれだけあるか」という
事実だけを言い、どう使うかは読み手に任せる。Seller Knowledgeを購入判断にしない
（[MVP仕様 §7](mvp-spec.md#7-seller-knowledge-indicator)）のと同じ線である。

利用者の案は「カード専門」「混ざっている」「カード少数」だった。**「カード少数」だけ「出品が少ない」に変えた。**
「カードが少ししか無い（ほかの物が多い）」とも読め、「混ざっている」と区別が付かないためである。
この山に入るのは、出品そのものが少なく、カード専門かどうかを言えない出品者である。

**「カード専門」は、ポケモンカードに限らない。**TCG全般の語で数えている（[§3.1](#31-計算)）。Tabの説明にそう書く。

#### 線の引き方

**「カード専門」の線は、カードの割合80%である**（2026-11-19に50%から直した）。

最初は50%だった。出品の幅の帯「狭い」（TCG比率50%以上。[§3.1](#31-計算)）を、そのまま「カード専門」にしていた。
利用者が、カード29件 / 53件（54.7%）の出品者を「カード専門」のTabで見つけた。**半分近くがカード以外の人を、専門とは呼ばない。**
50%は「幅が狭いか」を分けるために置いた仮の値で、名前を「カード専門」に変えたときに線も見直すべきだった。

| 候補 | 判断 |
|---|---|
| 50%のまま | 名前と合わない |
| 70% | 3割がカード以外の人も入る |
| **80%** | **利用者が選んだ** |
| 90% | 本物の専門店が外れやすい（下記） |

**線を高くしすぎない理由。**カードの割合は実際より低めに出る（[§3.4](#34-画面にはカードの割合として出す2026-11-19に直した)）。
Titleに「ポケカ」などの語を書かない専門店は、その分だけカード以外に数えられる。

**80%も測った値ではない。**[§11](#11-使ってみて見直すもの)に置いた。境界は「以上」の側へ入る（40件 / 50件はカード専門）。
割合ではなく件数の整数で比べる。80%ちょうどは、割り算の誤差で反対側へ落ちやすい。

この線はFrontendにある。Backendの帯（50% / 20%）は変えておらず、画面はそれを使っていない。

**「出品が少ない」を分けた理由。**カードを1枚だけ出している人は、出品の100%がカードなので、
幅は専門店と同じ「狭い」になる。しかしその人は、押入れから出てきた数枚を出している人かもしれない。
**3件の標本と300件の標本で、同じ「狭い」を同じ重さで読まない。**

線の30件は新しい値ではない。Seller Knowledgeが「標本の確からしさ」を低 / 中に分ける値
（[MVP仕様 §7](mvp-spec.md#7-seller-knowledge-indicator)）をそのまま使う。調べるのは販売中と売却済みの1ページ目ずつで、
1ページは最大30件なので（[PoC結果](../../poc/mercapi/result.md#seller商品一覧の30件上限・ページング追加検証)）、
**1人について読めるのは最大60件である。**

各行に出すものと操作は[§5.4](#54-1行に出すもの)と同じである（保存・除外・Mercariの出品者ページへのLink・`Sellerを分析`）。
断り書きも[§5.6](#56-断り書き)と同じものを出す。

### 12.6 「カード専門」をまとめて除外する

「カード専門」のTabにだけ、`このN人を除外リストへ入れる`を置く。

- **ほかの山には置かない。**「出品が少ない」と「未調査・不明」は、専門だと言える材料が無い
- 入れるのは[§6](#6-出品者リスト)の除外リストで、1人ずつ入れたときと同じである。**メモは空で入る**
- **Mercariへは何も送らない**
- 取り消すのは出品者リスト画面からである。まとめて戻す操作は無い

除外した出品者は、次に探すときから調べる対象に入らず、検索結果からも外れる（[§7](#7-検索結果からの除外)）。

**ボタンの隣には、押すと何が起きるかだけを書く。押すべきかは書かない。**

```text
除外リストへ入れた出品者は、次から調べる対象に入らず、検索結果にも出なくなります。
```

最初は、Tabの説明が「除外リストへ入れると、次からは調べる対象に入りません」と除外を促していた。
掘り出し物だけを探す日には、専門の出品者へ使う回数が減るので役に立つ。**美品を探す日には、同じ出品者が見に行く先になる**
（[§12.5](#125-4つの山)）。どちらの日かは読み手が決める。

### 12.7 探した範囲の記録

「取得する条件」の下に、何をどこまで取得したかを出す。検索画面の取得範囲（[MVP仕様 §5.4](mvp-spec.md#54-検索結果metadata)）と同じ役目である。

- キーワードごとに、取得した件数、ページ数、止まった理由。**取得できなかったキーワードはそう書く**
- まとめた件数と、出品していた出品者の人数（`12件の出品から 2人の出品者`）。**除外も絞り込みもする前の数である**
- 検索を途中で止めたこと

**記録は取得について述べる。誰を調べるかは「調べる出品者」の塊が述べる**（[§15.3](#153-調べる出品者の塊に出すもの)）。

### 12.8 止まるとき

扱いは[§4.3](#43-順番と停止)と同じで、**その失敗が誰についての事実か**で分ける。

| 起きたこと | 扱い |
|---|---|
| 検索が安全停止・429・Backendへ繋がらない | **そこで検索を止める。**次のキーワードを検索しない |
| 検索がそれ以外で失敗（Timeoutなど） | **次のキーワードへ進む。**記録に「取得できませんでした」と出す |
| 出品者を調べている途中の失敗 | [§4.3](#43-順番と停止)のとおり。止まったときは、そこまでの結果を残す。やり直すのは「調べる」で、検索はやり直さない |
| `止める`を押す | 今の1回（検索1つ、または出品者1人）が終わったら止まる |
| どのキーワードにも出品が無い | 「調べる出品者」の塊を出さず、その旨を出す |

**自動では再開しない。**

### 12.9 検索画面との関係

| 状態 | 検索画面と共有するか |
|---|---|
| 検索条件と検索結果 | **共有しない。**ここで探しても、検索画面の結果は変わらない |
| 出品者を調べた結果 | **共有する。**どちらで調べても、両方で調べ済みになる（[§4.4](#44-調べた結果の寿命)） |
| 出品者リスト | 共有する |
| 出品者を調べている最中かどうか | 共有する。**出品者を調べる操作は、同時に2つ走らせない。**片方が調べているあいだ、もう片方の「調べる」も、こちらの「検索」も始められない |
| 検索している最中かどうか | 共有しない。こちらが検索しているあいだに検索画面で検索すると、両方がBackendへ届く。**Mercariへは、Backendが同時実行1・2秒間隔で順に送る**（[architecture §4.1](../development/architecture.md#41-外部アクセスの条件と2秒間隔の出所)） |

結果の寿命は[§4.4](#44-調べた結果の寿命)と同じである。ほかの画面へ行って戻れば残り、再読み込みで消える。**保存しない。**

### 12.10 含めないもの

| 含めないもの | 理由 |
|---|---|
| **定期的に、または裏で探す** | [§2](#含めない)のまま。押した人が額を見てから払う |
| **キーワードの保存** | 保存するのは出品者についての読み手の決定だけである（[ADR 0004](../adr/0004-store-seller-lists-in-a-local-file.md)）。[§11](#11-使ってみて見直すもの)に置いた |
| **除外を自動で行う** | 「カード専門」は題名の語から読んだ見立てである。**除外するかは読み手が決める** |
| **Mercari上で出品者を検索する** | [§2](#含めない)のまま。候補は商品の検索結果から得る |
| **美品の軸で山を分ける** | 商品の状態は検索に出た出品についてしか分からない（[§5.2](#52-商品の状態は検索が既に持っている)）。各行には出すが、山は分けない |

## 13. タイトルに含む語（2026-11-19追加）

### 13.1 何が起きていたか

**Mercariのキーワード検索は、「すべての語を含む」ではない。**

利用者が`ポケモンカード　押入れ`（1つの欄、1回の検索）で探したところ、NARUTOカードゲームのまとめ売りが出た。
その出品のページを読むと、**「ポケモン」「ポケカ」は、タイトルにも説明文にもカテゴリーにも無い。**
「押入れ」は説明文にだけあり、「カード」は至るところにある（2026-11-19に確認。商品ID `m86185033032`）。

| 確かめたこと | 結果 |
|---|---|
| Card Diggerが語を分けて検索しているか | **分けていない。**入力した文字列は、そのまま1つの`keyword`としてMercariへ渡る |
| 検索画面と「出品者検索」で結果が違うか | **同じ。**利用者が、検索画面の「出品者」Tabで同じ出品を見つけた |
| その出品が語を含んでいるか | **含んでいない。**Mercariが返している |

**Mercariが語をどう扱っているかは、Card Diggerには分からない。**「ポケモンカード」が「ポケモン」と「カード」に
分かれ、合う語の多い出品が返っている、というのは見立てであって、確かめていない。

Mercariのアプリで同じ語を検索しても気づきにくいのは、既定の並びが「おすすめ順」で、合い方の弱い出品が沈むからである。
Card Diggerは古い出品まで届くために新しい順で取っており
（[MVP仕様 §5.3](mvp-spec.md#53-収集範囲)）、**そこでは弱い一致と強い一致が同じ段に並ぶ。**

「出品者検索」ではさらに目立つ。一致した出品が少ない出品者から調べるので
（[§12.4](#124-誰から調べるか)）、**弱い一致1件だけで見つかった出品者が先頭に来る。**

### 13.2 何をするか

**取得した後に、タイトルで絞る。**`タイトルに含む語`の欄に語を入れると、
**そのどれか1つをタイトルに含む出品だけを残す。**

```text
タイトルに含む語  [ ポケモン ポケカ ]
空白で区切った語の、どれか1つをタイトルに含む出品だけを残します。空欄なら絞りません。説明文は見ていません。
```

| 規則 | 内容 |
|---|---|
| 既定 | **空欄。何も絞らない。**読み手が語を入れるまで、結果は今までと同じである |
| 語の区切り | 空白（全角も）。**ここでは空白が区切りになる。**キーワードは1つの問いだが、こちらは言い換えの並びである |
| 一致 | **どれか1つ**を含めば残す。「ポケモンカード」と「ポケカ」は同じものの2つの書き方で、両方書く人はいない |
| 比べ方 | 全角 / 半角、大文字 / 小文字、ひらがな / カタカナを区別しない（`ﾎﾟｹｶ`、`ぽけか`、`ＰＯＫＥＭＯＮ`） |
| 絞る場所 | **Frontend。**取得した結果に対して行う。**Mercariへは何も送らない** |
| 適用 | **商品検索では、入力したそばから。**出品者検索では、「調べる」を押したとき（[§13.4](#134-出品者検索では誰を調べるかを決める)） |
| 順番 | 除外リストが先、タイトルが次、商品TabのFilterが最後（[§7](#7-検索結果からの除外)） |
| 範囲 | **検索画面の両方のTabと、「出品者検索」。語は2つの画面で同じものを使う。**片方だけに効くと、2つの画面がまた食い違う |
| 処理中 | **変えられない。**出品者を調べているあいだは欄を止める（[§15.4](#154-処理中は変えられない)） |
| 寿命 | 画面を開いているあいだだけ。**保存しない**（[§4.4](#44-調べた結果の寿命)と同じ） |

**語をCard Diggerが用意しない。**入力したキーワードから自動で絞ると、「ポケモンカード」で探した人から
「ポケカ」とだけ書いたタイトルが隠れる。何を同じものとして扱うかは、読み手が欄に書く。

### 13.3 隠したものを数える

外したものが1件でもあれば、件数を出す。**欄を空にすれば戻る。再取得しない。**

```text
検索画面        タイトルに「ポケモン」「ポケカ」のどれも含まない出品 37件を表示していません（出品者 29人は、ほかに残る出品がありません）
出品者検索  タイトルに「ポケモン」「ポケカ」のどれも含まない出品 37件は対象から外しています（出品者 29人は、ほかに残る出品がありません）。
```

**出品者の人数は「残る出品が1件も無い人」だけを数える。**1件が残り1件が外れた出品者は一覧に残っているので、数えない。

検索画面の取得範囲の記録には、Filterと同じく`指定した条件に一致: N件`を出す。記録が「取得した全件が画面にある」と読めてはいけない。

「出品者検索」で、見つかった出品がすべて外れたときは、そのことを書く。黙っていると「何も見つからなかった」と読める。

### 13.4 「出品者検索」では、誰を調べるかを決める

**出品者検索では、この語は表示の絞り込みではない。誰を調べるかを決める入力である**
（2026-11-19に改めた。[§15](#15-検索と調べるを別の押下にする2026-11-19追加)）。

外れた出品でしか見つからなかった出品者は、調べない。弱い一致で見つかった出品者に、1人3回を使わない。
**問い合わせの回数が変わるものを、表示の絞り込みとは呼ばない。**

| | 商品検索 | 出品者検索 |
|---|---|---|
| 置く塊 | 表示の絞り込み | **調べる出品者** |
| 効くとき | 入力したそばから | **「調べる」を押したとき** |
| 語を変えると | 表示がすぐ変わる | **一覧は変わらない。**次に「調べる」を押したときの対象が変わる |

**適用するのは、「調べる」を押した瞬間の語である。**押したあとに欄を変えても、調べる相手は変わらない
（そもそも、調べているあいだは欄を変えられない）。

**一覧は、最後に「調べる」を押したときの語で作ったものである。**欄を変えると、その旨を出す。

```text
語を変えました。「調べる」を押すと、下の一覧もこの語に切り替わります。
```

語を変えて「調べる」を押すと、新しく対象になった出品者だけを調べる。**検索はやり直さない。**
対象の全員が調べ済みなら、問い合わせは発生せず、一覧だけが切り替わる。ボタンの隣にそう書く。

### 13.5 O-7との違い

[O-7](../planning/todo.md#o-7--語彙で絞るのを今やらない理由2026-09-03)は、語彙で絞るのを保留している。
理由は「削った先が永久に見えない」だった。**この機能は、その理由に触れない形にしてある。**

| | O-7（保留のまま） | タイトルに含む語 |
|---|---|---|
| どこで絞るか | Mercariへ`excludeKeyword`を送る | 取得した後、Frontendで |
| 外れた出品 | **届かない。**何件あったか分からない | **手元にある。**件数を出す |
| 戻す | 取得し直す | 欄を空にする |
| 到達範囲 | 変わる | **変わらない** |

状態Filterと[O-9](../planning/todo.md#o-9--状態をmercariへ送るのを今やらない理由2026-09-04)の関係と同じである。
**逆に言えば、これは奥へ届く手段ではない。**弱い一致の出品は、1回の検索が取れる件数の枠を使ったままである。

### 13.6 限界

**検索結果は説明文を持たない**（[商品画面 §5.3](item-screen-spec.md#53-説明文)）。絞れるのはタイトルだけである。

```text
タイトル「カード まとめ売り」、説明文「押入れから出てきたポケモンカードです」
  → 「ポケモン ポケカ」で絞ると、外れる
```

**探している出品者（カードに詳しくない人）ほど、こういう書き方をする。**
だから既定は空欄で、外した件数を必ず出す。件数が多いと感じたら、欄を空にして見比べられる。

説明文まで見るには、出品1件ごとにMercariへ1回かかる。検索結果の数百件に対しては払わない
（[O-8](../planning/todo.md#o-8--sellerの活動で検索結果を絞るのを打ち切った理由2026-09-04)と同じ計算）。

### 13.7 キーワードの欄に書くこと

**キーワードを入力する欄の近くに、どこの一致を見ているかを書く。**検索画面と「出品者検索」の両方で、同じ文である。

```text
キーワードは、Mercariが商品名と商品の説明から探します。語をすべて含む出品だけが返るとは限りません。
```

| 文 | 出所 |
|---|---|
| 商品名と商品の説明から探す | Mercariのガイド「[商品の検索方法・検索条件の保存方法](https://help.jp.mercari.com/guide/articles/44/)」の記載（2026-11-19に読んだ） |
| すべて含むとは限らない | [§13.1](#131-何が起きていたか)の観測。**1件の観測である**ので、「限らない」までしか書かない |

利用者が、画面のどこかに簡潔に書いてほしいと言った（2026-11-19）。[§13.1](#131-何が起きていたか)の出来事は、
画面からは「語を分けて検索している」ようにしか見えなかった。**Mercariがすることでも、読み手の結果を変えるなら画面に書く。**

## 14. 取得する条件と、表示の絞り込みを分ける（2026-11-19追加）

**Mercariへ送るものと、取得した結果に対して手元で行うものを、別の塊に分け、この順に置く。**

**出品者検索は、同じ日にさらに改めた。**あいだに「調べる出品者」という3つ目の塊があり、
「表示の絞り込み」の塊は持たない（[§15](#15-検索と調べるを別の押下にする2026-11-19追加)）。
この節の「表示の絞り込み」は、今は商品検索についての記述である。

```text
取得する条件      Mercariへ送ります。変えたときは「検索」を押して取得し直します。
  キーワード、最低価格、最高価格、（出品者検索は）調べる出品者、Button、上限の回数

（取得した範囲の記録）

表示の絞り込み    取得した結果を手元で絞ります。Mercariへは送りません。
  除外リストで外した件数、タイトルに含む語、それで外した件数

（結果のTab）
```

### 14.1 なぜ分けるか

利用者の指摘である。出品者検索のFormは、キーワード → **タイトルに含む語** → 最低価格・最高価格 の順に並んでいた。
**Mercariへ送る問い（キーワード、価格帯）のあいだに、手元の絞り込みが挟まっていた。**
画面には、どれがどちらなのかを言うものが無かった。

この2つの違いは、この製品がいちばん大事にしている違いである。

| | 取得する条件 | 表示の絞り込み |
|---|---|---|
| 何を変えるか | **取得できる範囲**（[MVP仕様 §5.3](mvp-spec.md#53-収集範囲)） | 取得した中で、何を見せるか |
| 変えるとき | 押して取得し直す。Mercariへ問い合わせる | すぐ反映される。問い合わせない |
| 外れたもの | **届いていない。**何件あったか分からない | **手元にある。**件数が出て、戻せる |

利用者が手本に挙げたのは[tcg-buylist-watch](https://github.com/mgmaru/tcg-buylist-watch)で、
検索の欄のあとに、絞り込みと並べ方がそれぞれ名前の付いた箱として並んでいる。

### 14.2 置く順番

**取得する条件 → 取得した範囲の記録 → 表示の絞り込み → 結果。**記録は取得について述べるものなので、取得の側に置く。

| 画面 | 表示の絞り込みを出すとき |
|---|---|
| 商品検索 | 結果があるとき。結果が無いうちは、絞るものが無い |
| 出品者検索 | **出さない。**代わりに「調べる出品者」の塊を、検索の結果があるときに出す（[§15](#15-検索と調べるを別の押下にする2026-11-19追加)） |

### 14.3 表示の絞り込みは、問い合わせを変えない

最初は、この節に「1つだけ例外がある」と書いていた。出品者検索では、タイトルに含む語が誰を調べるかも決め、
問い合わせが減る、という例外である。

**例外ではなかった。**問い合わせを変えるなら、それは表示の絞り込みではない。利用者がそう指摘し、
出品者検索では語を「調べる出品者」の塊へ移した（[§15](#15-検索と調べるを別の押下にする2026-11-19追加)）。

商品検索では、表示の絞り込みのままである。「出品者」Tabの`まだ調べていないN人を調べる`は、
**読み手が、見えている出品者について押す操作**で、押す前にその人数と回数が出ている（[§4.1](#41-押したときだけ調べる)）。
絞り込みが勝手に問い合わせるのではない。調べているあいだは、欄を変えられない。

### 14.4 外した件数は、外した欄のそばに書く

タイトルに含む語で外した件数は、その欄のある塊に書く（[§13.3](#133-隠したものを数える)）。
商品検索では表示の絞り込み、出品者検索では「調べる出品者」である。
出品者検索では、はじめ「探した範囲」の記録に書いていた。**記録は取得について述べるもので、取得は何も変わっていない。**

### 14.5 この変更で動かしていないもの

**商品Tabの中の並び順とFilter**（掲載日、未更新日数、商品の状態、販売形式。[MVP仕様 §5.5](mvp-spec.md#55-sortとfilter)）は、
商品Tabの中に置いたままである。これらも表示の絞り込みだが、商品にしか効かない。
表示の絞り込みの塊は両方のTabに効くものだけを持ち、Tabの上にある。

## 15. 「検索」と「調べる」を、別の押下にする（2026-11-19追加）

### 15.1 3種類の操作

出品者検索ですることは、3種類ある。**それぞれを別の塊に置き、起きる順に並べる。**

| 種類 | 何を決めるか | Mercariへの問い合わせ | 変えられるとき |
|---|---|---|---|
| **取得する条件** | Mercariから何を取ってくるか（キーワード、価格） | 発生する（`検索`） | 押す前 |
| **調べる出品者** | 取ってきた中の、誰を調べるか（タイトルに含む語、一度に調べる人数） | 発生する（`調べる`） | 押す前 |
| **表示** | 済んだ結果をどう見せるか（Tab、良い評価での絞り込み、並び順。[§16.2](#162-表示の絞り込み・並べ替え)） | **発生しない** | 処理が止まっているとき |

**表示の絞り込み・並べ替えと呼ぶのは、3つ目だけである。**取得も、誰を調べるかの決定も終わり、
処理が動いていないときに、済んだ結果の見え方だけを変えるもの。問い合わせを一切変えず、戻せば元に戻る。
利用者がこの定義を示した（2026-11-19）。

### 15.2 どこから来たか

[§14](#14-取得する条件と表示の絞り込みを分ける2026-11-19追加)で2つの塊に分けたあと、利用者が2つ指摘した。

| 指摘 | 何がおかしかったか |
|---|---|
| 「調べる出品者（人数）」が最初の塊にあるのはおかしい | 人数は、Mercariの検索へ送る条件ではない。**検索の結果に対して掛けるもの**である。「取得と表示のあいだ」にある |
| データを取ったあと、出品者を調べている途中で「タイトルに含む語」を変えたら、どうなるのか | **整合が取れなくなっていた**（下記） |

2つ目は、当時の実装で実際に起きた。語は「検索が終わって、調べる相手を選ぶ時点」に読んでいた。

| 変えたとき | 起きたこと |
|---|---|
| 検索している最中 | 変えたあとの語で、調べる相手が選ばれる。**押したときの語ではない** |
| 出品者を調べている最中 | 調べる相手は変わらず、表示だけが新しい語に切り替わる。**調べ終えた人が消え、調べていない人が現れる** |

原因は、語を「表示の絞り込み」と呼びながら、誰を調べるかにも使っていたことである
（[§14.3](#143-表示の絞り込みは問い合わせを変えない)に、当時は「例外」と書いていた）。

### 15.3 「調べる出品者」の塊に出すもの

検索の結果があるときに出す。

```text
調べる出品者
  取得した結果の中から、誰を調べるかを決めます。「調べる」を押すと、1人につき3回Mercariへ問い合わせます。検索はやり直しません。

  タイトルに含む語  [ ポケモン ポケカ ]
  一度に調べる人数  [ 20人まで ]
  調べる順番        [ 一致した出品が少ない人から ]

  対象の出品者 12人（まだ調べていない人 12人）
  除外リストの出品者 2人・5件は対象から外しています。
  タイトルに「ポケモン」「ポケカ」のどれも含まない出品 37件は対象から外しています（出品者 29人は、ほかに残る出品がありません）。

  [ 調べる ]  Mercariへ36回問い合わせます（12人 × 3回。約2分以上）
```

**対象の人数と回数は、入力に追従する。押す前に、押したら何が起きるかが分かる。**
求めるのに問い合わせは要らない。出品は既に手元にある。

| 場合 | ボタンの隣に出すもの |
|---|---|
| 調べる人がいる | `Mercariへ36回問い合わせます（12人 × 3回。約2分以上）` |
| 人数の上限を超える | 加えて`人数の上限のため、今回調べるのは20人です。残り5人は、もう一度「調べる」を押すと続きから調べます。` |
| 対象の全員が調べ済みで、語が一覧と違う | `問い合わせは発生しません。対象の出品者は全員調べ済みで、一覧だけを切り替えます。` |
| 対象の全員が調べ済みで、語も同じ | `対象の出品者は全員調べました。`（押せない） |

### 15.4 処理中は変えられない

**出品者を調べているあいだ、タイトルに含む語と一度に調べる人数を変えられない。**欄を止め、`処理中は変えられません。`と出す。
商品検索の「タイトルに含む語」も、出品者を調べているあいだは同じく止める。

加えて、語は**押した瞬間の値**を使う。欄を止めるだけでは、もう一方の画面から同じ語を変えられる
（語は2つの画面で共有している。[§13.2](#132-何をするか)）。押したときに値として受け取り、あとから読みに行かない。

### 15.5 手放したもの

**1回押せば最後まで進む、という元の形。**[§12.1](#121-何のための画面か)の「繰り返しを手伝う」は、
キーワードをまとめて検索するところに残っているが、検索が終わってからもう一度押す必要がある。

1つのボタンのまま語を「調べる出品者」の入力にする案もあった。その場合、語を変えて調べ直すたびに、
検索もやり直すことになる（キーワード1つにつき最大10回）。**取ってきたものが手元にあるのに、取り直すことになる。**
利用者に両方を示し、分けるほうを選んだ。

### 15.6 一覧は、最後に「調べる」を押したときのもの

「調べる」を押すまで、一覧は出さない。新しく検索したあとも、もう一度押すまで出さない。
**その取得結果について、誰を調べるかを、まだ誰も決めていない。**
前の検索で調べた出品者は、調べた結果を覚えており（[§4.4](#44-調べた結果の寿命)）、また見つかれば調べ済みとして数える。

一覧の上に、何の一覧かを書く。

```text
タイトルに「ポケモン」「ポケカ」のどれかを含む出品の出品者を表示しています。
5人はまだ調べていません。もう一度「調べる」を押すと、続きから調べます。
```

## 16. 調べる順番と、結果の読み方（2026-11-19追加）

「調べる」の段階でも絞り込めないか、と利用者が尋ねた。例は2つだった。

- 良い評価が○件以上
- カード専門を優先して見つける

**答えは、それぞれの情報が「いつ分かるか」で決まる。**

| 分かる時点 | 分かること | 費用 |
|---|---|---|
| 検索が終わったとき | 出品者ごとの一致した出品の件数、その出品のTitle・状態・価格 | 追加なし |
| 調べるの1回目（Profile） | 名前、評価の内訳 | 1回 |
| 調べるの2〜3回目（商品一覧） | カードの割合 | さらに2回 |

**評価もカードの割合も、調べる前には分からない。**

### 16.1 調べる順番

「調べる出品者」の塊で、どちらの端から調べるかを選ぶ。

| 選択肢 | 並び | 当たりやすいと見ている相手 |
|---|---|---|
| `一致した出品が少ない人から`（初期値） | 件数の少ない順。同数は見つかった順 | 出品が混ざっている人、たまに出品する人 |
| `一致した出品が多い人から` | 件数の多い順。同数は見つかった順 | カード専門の人 |

**これは「カード専門を優先する」ではない。**専門かどうかは調べるまで分からず、それを決めるのが、この順番で調べる当の操作である。
できるのは、検索の時点で分かっている件数から、どちらの端に多そうかを見立てることまでである。
利用者も「これが直接、専門と混ざっているに直結するとは分からない」と確かめた。

そのため、**選択肢の名前は、することだけを言う**（「専門の人から」とは書かない）。欄の下に、見立てであることを書く。

```text
少ない人からは出品が混ざっている人に、多い人からはカード専門の人に当たりやすい、という見立てです。
どちらも確かめた値ではなく、調べるまで分かりません。対象が人数の上限に収まるときは、順番に関わらず全員を調べます。
```

**順番が結果を変えるのは、対象が一度に調べる人数より多いときだけである。**収まっていれば全員を調べる。

ほかの順（検索結果に出た順、一致した出品の状態が良い順）も、追加の問い合わせなしで作れる。
利用者と相談して、まず2つで始めた。選択肢が多いほど、どれを選ぶかで迷う。

処理中は変えられない（[§15.4](#154-処理中は変えられない)）。

### 16.2 表示の絞り込み・並べ替え

「調べる」を押したあと、結果のTabの上に出す。**[§15.1](#151-3種類の操作)の3つ目で、何をしてもMercariへは何も送らない。**

```text
表示の絞り込み・並べ替え
  調べ終えた結果の見え方だけを変えます。Mercariへは何も送らず、戻せば元に戻ります。

  良い評価 [ 100 ] 件以上    並び順 [ カードの割合が低い順 ]
  良い評価が100件に満たない出品者 3人を表示していません。評価の件数が分からない出品者は外していません。
```

| 項目 | 規則 |
|---|---|
| 良い評価 | 0以上の整数。空欄なら絞らない。**その件数以上**の出品者を残す |
| 件数が分からない出品者 | **外さない。**まだ調べていない人、Profileに内訳が無かった人。「少ない」と言った人はいない（[MVP仕様 §5.5](mvp-spec.md#状態不明を落とさない)と同じ） |
| 並び順 | `カードの割合が低い順`（初期値）/ `カードの割合が高い順` / `良い評価が多い順` / `一致した出品の状態が良い順` / `一致した出品が多い順` |
| 分からない値の並び | どの順でも最後。0や最低として扱わない |
| 外した人数 | 1人でもいれば出す |
| 寿命 | ほかの画面へ行って戻っても残る。再読み込みで消える。**保存しない** |
| 処理中 | 変えられない |

`検索結果に出た順`は、ここには置かない。複数の検索をまとめた結果には、誰のものでもない順しか残らない。
商品検索の「出品者」Tabには、これまで通りある。そちらの並び順にも`カードの割合が高い順`と`良い評価が多い順`を足した。

「カード専門」をまとめて除外するボタン（[§12.6](#126-カード専門をまとめて除外する)）は、**表示されている人**に対して働く。

### 16.3 調べる途中で打ち切らない

良い評価で絞る方法は2つあった。

| | A. 調べ終えたあと、表示で絞る | B. 調べる途中で打ち切る |
|---|---|---|
| 仕組み | 3回とも問い合わせてから、表示で外す | Profileを取り、足りなければ残り2回を送らない |
| 問い合わせ | 変わらない | 外れた人1人につき2回減る |
| 戻す | 欄を空にする | **問い合わせ直す** |
| 回数の表示 | 実数のまま | 1人1〜3回になり、上限に戻る |

**Aを採った。**

- **目的と逆に働く場面がある。**評価の少ない人は、たまにしか出品しない人である。掘り出し物を探すときに探しているのは、その人たちである。
  Bで打ち切ると、その人の出品の中身は分からないままになる
- **回数を実数で出せなくなる**（[§15.3](#153-調べる出品者の塊に出すもの)）
- **評価の件数は、出品の経験とは限らない。**購入者としての取引でも評価は付く、と理解している（Card Diggerでは確かめていない）。
  打ち切りの根拠にするには弱い

Bが割に合うのは、評価の少ない人が大半で、しかも見る気が一切無い、と分かったときである。[§11](#11-使ってみて見直すもの)に置いた。

### 16.4 入れなかったもの

**一致した出品の状態で、調べる相手を絞る。**状態は検索の時点で分かっているので、追加の問い合わせなしで作れる。
「美品を出している出品者」は最初に挙がった2軸の1つ（[§1](#1-目的)）である。利用者に示し、今回は入れていない。
