# Phase 0 共通検証プロトコル

## 1. 目的

`marvinody/mercari`、`kynacio/mercapi`、Playwrightの3方式を、同じ入力・停止条件・評価方法で比較する。検証結果の差が検索条件や測定方法の違いではなく、取得方式の違いから生じる状態を作る。

実行時の正本は [`poc/common/conditions.json`](../poc/common/conditions.json) とする。この文書は値の意味と測定手順を定義する。

## 2. 固定する検索条件

| 項目 | 値 | 理由 |
|---|---|---|
| キーワード | `ポケカ 引退品` | MVPの中心ユースケースであり、一定数の検索結果が期待できる |
| 販売状態 | `on_sale`（販売中） | 購入候補だけを対象にする |
| 並び順 | `created_time ASC`（古い順） | 本アプリが解決したい主要課題を直接検証する |
| カテゴリ | 指定なし | 方式ごとのカテゴリ体系や絞り込み差を持ち込まない |
| 最低・最高価格 | 指定なし | 取得可能範囲を価格で狭めない |
| 認証状態 | ログインなし | 個人アカウントや永続Cookieへの依存を避ける |
| ロケール・タイムゾーン | `ja-JP` / `Asia/Tokyo` | 日時表示と記録条件を統一する |

古い順指定を受け付けない方式でも検証は継続し、実際に使用された並び順、クライアント側ソートの有無、最古商品の日時を記録する。取得後のクライアント側ソートだけでは「古い商品まで遡れる」と判定しない。

## 3. 共通の取得モデル

各方式のレスポンスを次の項目へ正規化する。元レスポンスのフィールド名と、追加リクエストまたは値の生成が必要だったかも記録する。

| 項目 | 正規化ルール |
|---|---|
| `itemId` | 空でない文字列。ページ間の重複判定キーに使う |
| `title` | 空でない商品タイトル |
| `priceYen` | 1円以上の整数。通貨は日本円 |
| `itemUrl` | `https` の商品URL。IDから生成した場合は `generated` と記録する |
| `imageUrls` | `https` のURL配列。最低1件を取得成功とする |
| `createdAt` | 解析後はRFC 3339形式で保存し、元の値も検証ログに残す |
| `status` | `on_sale` / `sold_out` / `unknown` のいずれか |
| `sellerId` | 空でない文字列。取得不能時は `null` |
| `sellerName` | 空でない文字列。取得不能時は `null` |

商品フィールドは最初の100ユニーク商品を母数にする。Seller名など追加アクセスが必要なSeller情報は、取得順で最初に現れる10人のユニークなSellerを母数にする。

## 4. 実行環境の記録

検証結果には次を必ず記録する。

- 実行日時とタイムゾーン
- GitコミットSHA
- OS、CPUアーキテクチャ
- PythonまたはNode.jsのバージョン
- 対象ライブラリのバージョンまたはコミットSHA
- 直接依存パッケージとバージョン
- Headless / Headedの別
- Cookie、Token、ログイン、Proxyの要否（値そのものは記録しない）
- 実行したコマンド

市場の検索結果は時間とともに変化するため、3方式の本測定は可能な限り同じ端末・ネットワークで24時間以内に行う。

## 5. 測定手順

### 5.1 検索安定性

1. 各試行を新しいプロセスで実行し、前回のインメモリ状態を引き継がない。
2. 同じ検索条件で5回試行する。
3. 自動再試行は行わない。再試行を実装した測定は補足結果として分離する。
4. 試行間およびページ間は2秒以上空け、同時実行数は1とする。
5. 各試行の成否、エラー分類、処理時間、取得件数を記録する。

1回の検索成功は、60秒以内に処理が完了し、致命的な通信・解析エラーがなく、必須項目を持つ商品を1件以上返した場合とする。

### 5.2 ページングと古い商品

ページングは1回の独立した測定として、次のいずれかまで継続する。

- 100ユニーク商品以上を取得し、365日以上前の商品を1件以上取得した
- 次ページが存在しない
- 20ページに到達した
- 1,000ユニーク商品に到達した
- 安全停止条件に該当した

ページ番号またはCursor、ページごとの件数、重複商品数、累計ユニーク件数を記録する。「十分古い商品」の暫定基準は検証実行日時から365日以上とする。

### 5.3 Seller情報

商品から取得できたSeller IDを出現順に重複排除し、最大10人についてProfileを取得する。Seller ID、Seller名、Profile取得成否、追加リクエスト数、エラーを記録する。

売却済み商品やSellerの商品一覧はPhase 0-A〜0-C固有の追加検証とし、この共通ベースラインの成功率には含めない。

## 6. 指標と合格目安

| 指標 | 算出方法 | 合格目安 |
|---|---|---:|
| 検索成功率 | 成功試行数 / 5 | 80%以上。100%を優先 |
| 取得件数 | ユニークな`itemId`数 | 100件以上 |
| 重複率 | 重複出現数 / 全出現数 | 参考値として比較 |
| 必須項目取得率 | ID・タイトル・価格・URL・状態を取得できた商品数 / 対象商品数 | 各100% |
| 画像URL取得率 | 画像URLを1件以上取得できた商品数 / 対象商品数 | 95%以上 |
| 出品日時取得率 | 正常に日時解析できた商品数 / 対象商品数 | 95%以上 |
| Seller ID取得率 | Seller IDを取得できた商品数 / 対象商品数 | 95%以上 |
| Seller名取得率 | Seller名を取得できたSeller数 / Seller標本数 | 90%以上 |
| 古い商品到達 | 出品から365日以上の商品を取得したか | 1件以上 |
| 実行速度 | プロセス全体と検索処理の経過時間 | 中央値・最大値を比較 |
| HTTP/APIエラー | 401 / 403 / 429 / Timeout / Parse Errorの件数 | 0件を優先 |

閾値未達でも測定値は破棄しない。必須情報を追加の商品詳細リクエストで補える場合は、補完後の取得率、総リクエスト数、追加時間を分けて記録する。

## 7. 実装・保守性の比較

### 実装の複雑さ

次の客観値を記録してから、`低 / 中 / 高` を判定する。

- PoCの実コード行数（生成物とテストデータを除く）
- 直接依存パッケージ数
- 初回セットアップのコマンド数
- Browser、Cookie、Token、手作業の要否
- ページング、レスポンス変換、再試行に必要な独自コード

### Mercari仕様変更への耐性

次を根拠に `低 / 中 / 高` を判定する。

- 非公開Endpoint、レスポンス構造、DOM、通信Interceptへの依存範囲
- 外部ライブラリ内に変更影響を閉じ込められるか
- 型定義・自動テスト・固定レスポンスFixtureの有無
- 対象プロジェクトの更新状況
- 破損を検知できるエラー処理とテストの有無

## 8. エラー分類と安全停止

エラーは少なくとも `unauthorized_401`、`forbidden_403`、`rate_limited_429`、`timeout`、`parse_error`、`challenge`、`network_error`、`unknown` に分類する。

次の場合はアクセスを停止し、回避を試みず結果へ記録する。

- 401、403、429、Challenge/CAPTCHAが合計3回連続した
- 対象サービスが待機時間を明示した
- 予期しない大量リクエストが発生する挙動を確認した

Rate Limitは通常のPoC実行中に受動的に観測する。制限値を特定するための高負荷試験は行わない。認証回避、CAPTCHA回避、複数アカウント・Proxyによる制限回避も検証対象外とする。

## 9. 結果の保存

各PoCの結果は [`poc/common/result-template.md`](../poc/common/result-template.md) をコピーし、方式ごとのディレクトリへ `result.md` として保存する。

生レスポンス、スクリーンショット、Traceは各方式の `artifacts/` に保存できるが、Git管理外とする。結果MarkdownへCookie、Token、個人情報を転記せず、必要な例示データはマスクする。
